# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TexFlow (package name `sistema-confeccao`) is a front-end-first prototype, evolving into a real client-server app, for managing the production workflow of a garment manufacturer ("confecção") called **Kavi**, from sale to delivery. UI copy and domain terms are in Portuguese (pedidos, clientes, produção, etc.) — keep new UI text consistent with that. Data lives in a real Node/Express + PostgreSQL backend (`backend/`) as of the backend migration's step 5 (2026-07-06) — React Context Providers (`src/context/`) now fetch from and persist through that API instead of seeding in-memory from `src/data/*.js`. This backend was built specifically because Kavi will have multiple people (vendedora, produção) using the system from different computers — see "Backend migration roadmap" below for what's done and what's still ahead (deploy, auth/roles).

**TexFlow is explicitly NOT a full ERP.** It is not a financial system and not a fiscal/invoicing system. Its sole focus is controlling production flow: registering orders, tracking each product through its stages, surfacing bottlenecks, and organizing files/comments/history per product. Do not add invoicing, accounting, or tax-related scope unless the user asks.

## Domain model (read before touching order/product/production logic)

This is the most important — and least obvious from the code alone — part of the architecture. It was worked out deliberately with the user and should not be re-litigated without their input.

- **An order (`pedido`) contains multiple products (`produtos`).** E.g. order 125 = 80 t-shirts + 30 caps + 20 polos, all one order.
- **Three stages belong to the order as a whole, happen once, and are shared by every product in it**: Venda (sale) → Design → Aprovação (approval).
- **After approval, each product follows its own independent workflow.** Tracking/status must be done per-product, not per-order. Different products in the same order can be in completely different stages at the same time (e.g. the t-shirt is in Costura while the cap is already in Bordado).
- **Workflow per product is chosen manually, per product, from a configurable operations list** — it is not one fixed pipeline and not auto-inferred from product type. Example variations:
  - Camiseta: Costura → Silk → Revisão/Finalização
  - Boné: Bordado → Embalagem
  - Camisa Polo: Costura → Bordado → Revisão/Finalização
- **Available operations**: `src/data/operations.js`'s `DEFAULT_OPERATIONS` (Corte, Costura, Bordado, Silk, DTF, Lavagem, Revisão/Finalização, Embalagem) is only the **seed** list now — the live, editable list lives in `OperationsProvider`'s context (`src/context/`), managed from the `Settings` screen (2026-07-03). The product form also accepts a free-text "outra operação" for one-off steps not in the list — those get folded into the same selection, not stored separately.
- **Bordado (embroidery), Silk (screen printing), and DTF (direct-to-film printing) are independent operations** — a product can need any combination of them, or none; they do not depend on each other. (Earlier discussion called this generically "Estampa" — Silk/DTF is the more precise, current vocabulary; don't reintroduce a generic "Estampa" field.)
- **Operations have a production sequence, modeled as layered "positions" (✅ built, 2026-07-06), not a single linear order.** Each operation in the catalog (`operations.sequence_position`, an integer) sits at a layer; an operation can only start (`status` leaving `'pending'`) once every *other selected operation on that same product* with a strictly lower position is `'done'` — operations sharing the same position are independent of each other and don't gate one another. Current layout: `1` Corte → `2` Bordado/Silk/DTF/Costura (siblings — Costura does **not** wait on Bordado/Silk/DTF, only on Corte, because their relative order can vary job to job) → `3` Revisão/Finalização (waits for all *selected* position-1 and position-2 steps) → `4` Lavagem → `5` Embalagem. **The gate only blocks the start of a step** — once a step leaves `'pending'`, it can move freely (including back to an earlier status) regardless of what happens to other steps afterward; this was a deliberate simplification over gating every forward transition. A custom "outra operação" step with no matching row in the `operations` catalog (or a catalog row with `sequence_position = NULL`) is exempt on both sides: it's never blocked, and it never blocks anything else. Enforced server-side only, in `PATCH /products/:id/workflow/:step` (`backend/src/routes/products.js`, via `findBlockingSteps` in `backend/src/db/ordersQueries.js`) — rejects with `409` and a message naming the still-pending steps. **No frontend gating/disabling was added** (e.g. graying out "Iniciar" before the fact) — clicking it just surfaces the 409's message via the existing `alert()`-on-failure pattern already used everywhere else; proactive UI polish here was deliberately skipped, consistent with "Visual polish (intentionally deferred)" below. Positions aren't exposed as configurable-via-drag-and-drop; `Settings` just gained a plain numeric "Posição (opcional)" input next to the existing add-operation text field, so **new** operations can be slotted in immediately — reordering the *existing* ones still means editing the position number by hand (no bulk reorder UI).
- **Placement of embroidery/print (frente, costas, manga direita/esquerda, combinations, etc.) is deliberately NOT modeled as structured fields.** It's a single free-text observations field (e.g. "Bordado no peito esquerdo", "Silk frente e manga"). This was a conscious simplification — do not "improve" it into separate location/side/position fields without the user asking.
- **A product's workflow is stored as `product.workflow: [{ step, status }]`**, where `status` is `'pending' | 'in_progress' | 'done'`. Selecting/deselecting operations only changes which steps exist in the array; re-editing a product must preserve the `status` of steps that survive the edit (don't reset progress just because the operations were touched again) — see `saveWorkflow` in `src/hooks/useProductList.js`.
- **Choosing *which* operations a product needs is a sales-time decision, not a production-time one.** The vendedora already knows this when taking the order — the client is the one asking for "bordado no peito" or "silk nas costas" — so it must be selectable immediately when a product is created, with no gate tied to `order.stage`. What legitimately *can't* happen before the order reaches `'producao'` is a chosen operation's `status` advancing from `pending` to `in_progress`/`done` — that's physical work starting, which needs the approved artwork. **Don't reintroduce a gate on selecting operations** (an earlier version of this app briefly did, and it was wrong — see "Important nuance" below); if you build the future production board, gate *status advancement* there instead.
- **Per-product entities planned**: tipo, modelo, cor, tecido, quantidade, observações, status, workflow próprio (see above), arquivos próprios (files belong to the product, not the order — arte frente/costas, logo, arquivo de bordado, mockup, manual), comentários internos (built 2026-07-03, see Architecture below — internal-only, never shown to the client), histórico (timestamped event timeline, e.g. "08:00 Costura iniciada", "09:30 Costura finalizada" — still not built, don't confuse with comments; a comment is a free-text note, history would be an automatic log of state changes).
- **Modelo (model) is a distinct, meaningful field** from tipo — e.g. "Camiseta Raglan" vs "Camiseta Tradicional" — plus its own free-text observations for construction details (e.g. "recorte lateral cinza").
- **Per-product files (✅ built, 2026-07-06) have two categories, tied to two different moments in the flow, not one generic "attachments" bucket.** `'referencia'` = material the vendedora receives from the client *at the sale itself* (photos, the client's logo, a fabric-tone reference) — needed by design to build the mockup, so upload must be available immediately at product creation (`NewOrder`'s and `OrderDetails`' add-product wizard, 'info' step), not gated behind any later step. `'layout_aprovado'` = the final approved mockup PDF, consulted afterward by every production sector (costura, bordado, silk, corte, DTF, etc.) as the reference for how the piece should turn out — this only exists after client approval, so it's uploaded later, but **deliberately has no stage gate either** (confirmed with Pablo — same "don't add gates nobody asked for" philosophy as operation selection). Both categories can also be added **after** the product already exists, any time, via a `ProductCard` "Arquivos" button/modal (mirrors the existing "Comentários" modal exactly). Files never touch the app's own server disk — actual bytes go to **Cloudinary** (chosen for its free tier and minimal setup versus S3/R2 at this scale); the DB only stores the resulting URL (`product_files.file_url`).

## Architecture

- **Stack**: React 19 + Vite 8, `react-router-dom` v7 for routing. Plain JSX (`.jsx`, no TypeScript). Vanilla CSS files (one per feature area under `src/styles/`), no CSS modules or CSS-in-JS.
- **Routing** (`src/App.jsx`): a single `BrowserRouter` with all routes declared flatly — `/`, `/login`, `/pedidos`, `/pedidos/novo`, `/pedidos/:id`, `/clientes`, `/design`, `/producao`, `/relatorios`, `/configuracoes`. `/pedidos/novo` is declared **before** `/pedidos/:id` deliberately — this fixed a real bug where "novo" was being swallowed by the `:id` param. Preserve this ordering (specific static routes before dynamic ones) when adding routes.
- **Layout**: every page (except Login) wraps its content in `<Layout>` (`src/components/layout/Layout.jsx`), which renders the `Sidebar` nav plus a `<main className="content">` slot. Follow this convention for any new page.
- **Pages** (`src/pages/*/index.jsx`, not `<Name>.jsx`): deliberate choice over flat files so a growing page can gain siblings (`DashboardCards.jsx`, `dashboard.css`, etc.) without cluttering `pages/`. Historically each page defined its own mock data inline as local arrays/objects, but that's no longer true anywhere — `Dashboard` and `Reports` (both fixed 2026-07-07) were the last two still doing that, and `Login` (fixed 2026-07-06, see the auth step in the backend migration roadmap) was the last unimplemented stub. Every page now reads real data through `useOrders()`/`useClients()`/`useOperations()` or, for `Reports`, its own `reportsApi` calls.
- **`src/data/orders.js`** (`initialOrders`) seeds the shared store below with 3 demo orders (each with real nested products/workflows) — this used to be an empty placeholder. `src/data/clients.js` (`initialClients`, `getClientDisplayName`) likewise seeds the clients store — also no longer an empty placeholder. `products.js` is still an empty placeholder, not yet wired into any page.
- **`src/components/ui/`** vs **`src/components/layout/`**: `ui` holds generic reusable presentational components (`Button`, `Input`, `Card`, `Modal`, `Select`, `Textarea`, `Badge`, `ProductCard`) — chosen over the earlier `components/common` naming to match common React convention. Before building new UI, ask "can this be a reusable component?" — if yes, add it to `ui/` rather than inlining markup in a page. `Textarea` and `Select` are implemented (both mirror `Input`'s prop shape — `Textarea` adds `rows`, `Select` adds `options: [{ value, label }]`), e `FileInput` (2026-07-29) cobre `<input type="file">`, que não cabe no `Input` por ser sempre não-controlado; `Badge` segue como stub vazio.
- **`Button`** takes a `variant` prop (`primary`/`secondary`/`danger`) mapped to a `btn-{variant}` class — follow this pattern for new variants rather than adding one-off className logic.
- **`ProductCard`** is the single reusable representation of a product (icon, modelo, cor, quantidade, status, observações, editar/excluir/comentários actions), reused across Novo Pedido and Detalhes do Pedido (and meant for Produção/Relatórios too) rather than re-implemented per screen. It computes an overall status badge from `product.workflow` (`Não iniciado` / `Em andamento` / `Concluído`) and renders each workflow step as a chip color-coded by that step's own `status` (`workflow-chip-pending|in_progress|done`) — so a product's progress is visible without opening anything else. `.product-card` and its sub-elements went **years of project-time with zero CSS** (a documented, intentional gap) — first real styles landed in the 2026-07-10 polish pass (`src/styles/products.css`); see "Visual polish" below.
- **`src/context/` is the shared front-end cache of the backend for the whole app** (before step 5 of the backend migration it was genuinely the in-memory database; now `OrdersProvider` fetches from and persists through the real API — see "Backend migration roadmap" below) — split into two files on purpose:
  - `ordersContext.js` (plain `.js`, no JSX) exports the raw `createContext()` result and a `useOrders()` hook (`useContext` wrapper). Any page/hook calls `useOrders()` to read `orders` or call a mutator.
  - `OrdersProvider.jsx` owns the actual `orders` array as `useState` (fetched from `GET /orders` on mount, kept in sync by every mutator's response) and exposes all the mutators: `createOrder`, `finalizeOrder`, `updateOrderInfo`, `advanceOrderStage`, `addProduct`, `removeProduct`, `updateProductWorkflow`, `moveProductStepStatus`, `toggleProductDesignRework` — every one of these is now `async`, returning the created/updated resource on success or `null` on failure (after already alerting the error itself). Every order embeds its own `products` array — this mirrors the domain model directly (an order *contains* products, not a parallel list keyed by order id).
  - **Every order created via `createOrder()` starts with `isDraft: true`** (the column's DB default, `backend/src/db/schema.sql`), and only flips to `false` via `finalizeOrder(orderId)`. `Orders` and `Production` both filter out draft orders (`orders.filter(order => !order.isDraft)`) before showing anything. This exists because `NewOrder` creates its order in the shared store the moment the page mounts — without the draft flag, a half-filled or abandoned order would already be visible to everyone else.
  - They're split into two files because of a real ESLint rule (`react-refresh/only-export-components`): a `.jsx` file that exports both a component (`OrdersProvider`) and a non-component (`useOrders`) breaks Vite's Fast Refresh. Keep this split — don't merge them back into one file.
  - `<OrdersProvider>` wraps `<BrowserRouter>` in `src/App.jsx`, so every routed page can call `useOrders()` regardless of where it sits in the route tree.
- **`src/context/clientsContext.js` + `ClientsProvider.jsx`** mirror the same split-file pattern, as a second, independent context — clients are a distinct entity from orders, not a field owned by `OrdersProvider`. `ClientsProvider` owns `clients` (seeded from `src/data/clients.js`) and exposes `addClient(client)` and `findOrCreateClient(clientInfo)`. `<ClientsProvider>` wraps `<OrdersProvider>` in `App.jsx` (nesting order between the two doesn't matter — they don't depend on each other).
- **A client is `{ id, personName, companyName, document, phone, email }`**: `personName`, `document` (CPF/CNPJ), and `phone` are required; `companyName` and `email` are optional. `getClientDisplayName(client)` (`src/data/clients.js`) is the one place that decides what to *show* for a client — company name if present, else the person's name — use it instead of reading `client.companyName`/`client.personName` directly in JSX.
- **An order references a client via `order.clientId`, not a free-text name.** This replaced an earlier `order.client` string field entirely (2026-07-03) — the user asked for orders to cross-reference real client records instead of comparing typed-in names. **Matching is by `document` (CPF/CNPJ) only, not phone** — a deliberate call: phone numbers can be shared (a shared landline, a family), so they're not a safe uniqueness key, while a CPF/CNPJ is. `findOrCreateClient` in `ClientsProvider` looks up by `document`; if no client has that `document` yet, it creates one and returns the new id. Don't change this to match by phone, or by "phone or document" — document is intentionally the sole key.
- **`src/components/ui/ClientFields.jsx`** is the one reusable form (the 5 client fields, wrapped in `.form-grid`) used by `Clients`' "Adicionar Cliente" modal directly, and by `ClientAutocomplete` (below) as its manual-entry fallback — don't duplicate these five `<Input>`s a third time; extend `ClientFields` instead.
- **`src/components/ui/ClientAutocomplete.jsx`** (2026-07-04) wraps `ClientFields` with a search-existing-client step, used in `NewOrder`'s "Informações Gerais": typing into "Buscar cliente existente" filters `clients` by `personName`/`companyName`/`document` (first 5 matches, shown as a plain list below the input — not an absolutely-positioned dropdown, kept simple on purpose); clicking a match calls `onChange(selectedClient)` with the *entire* client record, and the component then shows a compact read-only "cliente selecionado" summary + "Trocar cliente" button instead of the editable fields (this prevents accidentally editing a selected client's `document` and silently detaching the order from the right record). If nothing is selected, `ClientFields` stays visible/editable underneath the search box for registering a brand-new client — exactly the old behavior. **This component owns no server-of-truth logic** — it just bubbles the full client object up via `onChange`; `NewOrder`'s existing `findOrCreateClient(clientDraft)` call at finalize time didn't need to change at all, since a selected existing client's `document` already matches an existing record.
- **`src/components/ui/ProductFields.jsx`** (2026-07-04) extracts the product-info form (tipo/modelo/cor/tecido/quantidade/observações) that used to be duplicated verbatim in both `NewOrder` and `OrderDetails` — both now render `<ProductFields product={product} onChange={handleChange} />` in the add-product modal's `'info'` step. `Modelo`/`Cor`/`Tecido` use `SuggestibleInput` instead of plain `Input`.
- **`src/components/ui/SuggestibleInput.jsx`** is a generic single-field text input with a suggestion dropdown — deliberately **not** the same pattern as `ClientAutocomplete`: it doesn't lock into a "confirmed" state, doesn't replace other fields, and just fills its own `value` on suggestion click, exactly like typing would. `ProductFields` derives each field's suggestions live from every product across every order (`orders.flatMap(order => order.products)`, distinct non-empty values per field via `getDistinctValues`) — there is no separate managed catalog, unlike `DEFAULT_OPERATIONS`/`OperationsProvider`; the user explicitly wants free text with reuse-what-was-typed-before suggestions, not a rigid dropdown. **Gotcha worth preserving**: the suggestion buttons use `onMouseDown` (not `onClick`), and blur hides the list on a `setTimeout` — clicking a suggestion while the input has focus fires blur before a plain `onClick` would register, so `onClick` alone would make suggestions unclickable.
- **`NewOrder` holds client info as a local draft (`clientDraft`), separate from the order itself**, until "Finalizar Pedido" is clicked. Only then does it call `findOrCreateClient(clientDraft)` and attach the resulting id via `updateOrderInfo(orderId, { clientId })`. This mirrors the same "draft, then commit" pattern already used for products — it avoids calling `findOrCreateClient` on every keystroke (which would risk creating a client from a half-typed CPF/CNPJ before the vendedora finishes typing).
- **`Clients` (`/clientes`)** lists every client with a computed order count/history (`orders.filter(order => !order.isDraft && order.clientId === client.id)`) and an "Adicionar Cliente" modal that blocks saving a duplicate `document` with an `alert`. This is a direct client-registration flow — separate from (and not gating) `NewOrder`'s find-or-create path.
- **`src/context/operationsContext.js` + `OperationsProvider.jsx`** are a third, independent context (same split-file pattern) owning the live list of production operations, seeded from `DEFAULT_OPERATIONS`. `Settings` (`/configuracoes`) is now a real page: lists every operation with a "Remover" button, plus an add-new-operation row (reusing `.operation-custom`, the same class `OperationsChecklist`'s "outra operação" row uses). `OperationsChecklist` and `Production`'s `.tabs` row both read from `useOperations()` instead of importing `DEFAULT_OPERATIONS` directly — an operation added in Settings shows up immediately in both places. **Removing an operation doesn't touch any product that already has it selected** — `OperationsChecklist`'s existing `extraSteps` logic (steps in `selectedSteps` but not in the base list) already renders it as a still-checked, no-longer-in-the-base-list option, so this "just worked" without extra code.
- **`src/hooks/useProductList.js`** now takes an `orderId` and reads/writes that order's products **through `useOrders()`** — it no longer owns the products array itself. It still centralizes all the *UI-only* state (which modal is open, the draft form fields, `selectedSteps`) and the add-product wizard / edit-workflow logic, so `NewOrder` and `OrderDetails` share the exact same logic instead of duplicating it. Any future screen that manages a product list should use this hook rather than reimplementing it — just pass it the relevant `orderId`.
- **Per-product internal comments** (`product.comments: [{ id, author, text, createdAt }]`) are a third modal managed by `useProductList` (`isCommentsModalOpen`/`commentingProduct`/`commentDraft`/`openCommentsModal`/`closeCommentsModal`/`addComment`), opened via a "Comentários" button on `ProductCard` (shows a count, e.g. "Comentários (2)", when non-empty). Newest comment shows first (`.slice().reverse()`, doesn't mutate the stored array). `OrdersProvider.addProductComment(orderId, productId, comment)` appends to the array. **`author` is a free-text field the person fills in themselves — there is no login system yet**, so there's no way to know who's actually typing; don't assume this is a real authenticated identity. Once real auth exists, this should auto-fill from the logged-in user instead of being a manual `Input`.
- **Per-product files** (✅ built, 2026-07-06 — see domain model above for the two categories) are a fourth modal, same shape as comments: `isFilesModalOpen`/`filesProduct`/`fileDraft`/`selectedFile`/`openFilesModal`/`closeFilesModal`/`uploadFile` in `useProductList`, opened via a new "Arquivos" button on `ProductCard`. **One real sequencing wrinkle, unlike comments**: a "referência" file can be attached *during the add-product wizard's 'info' step*, before the product exists in the database yet — `referenceFiles` holds raw browser `File` objects in local state (`addReferenceFile`/`removeReferenceFile`), and `saveNewProduct` only actually uploads them (looping over `referenceFiles`, one `addProductFile` call each) *after* `addProductToOrder` succeeds and returns the product's real id; nothing is uploaded if product creation itself fails. Backend: `backend/src/services/cloudinary.js` wraps the Cloudinary Node SDK (`cloudinary.config()` reads `CLOUDINARY_URL` from the environment automatically) with a small `uploadBuffer()` helper using `upload_stream` — files are held in memory (`multer({ storage: multer.memoryStorage() })` in `backend/src/routes/productFiles.js`) and streamed straight to Cloudinary, **never written to the container's own disk** (irrelevant for correctness locally, but would be silently lost on every Railway redeploy if it ever touched disk there, since that filesystem is ephemeral). `POST /products/:id/files` validates `category` is one of the two allowed values before uploading (fails fast, doesn't waste an upload on a bad request), and `product.files` is now embedded in the product shape everywhere else already returns `workflow`/`comments` (`mapFile`/`mapProduct` in `ordersQueries.js`). **No delete route** — matches the existing comments precedent (add-only, no edit/delete there either); an orphaned file left behind in Cloudinary after a product/order is deleted is a known, accepted gap, not handled. Requires a `CLOUDINARY_URL` env var (`.env.example` in both `backend/` and set on Railway) — **non-obvious deploy gotcha hit while building this**: `railway restart` does **not** pick up a variable changed after the last real deploy (it seems to reuse that deployment's captured environment snapshot) — only a fresh `railway up` actually bakes in the current variable values, confirmed by hitting a genuine "Invalid Signature" Cloudinary error that only went away after a real redeploy, not a restart.
- **`NewOrder` creates a real (draft) order on mount**, via `createOrder()` from the context, and keeps its id in local state. Because `<StrictMode>` (in `main.jsx`) intentionally double-invokes effects in development to catch impure side effects, the creation is guarded with a `useRef` flag (`hasCreatedOrder`) so it only actually runs once — without this guard, opening `/pedidos/novo` in dev would silently create two orders. The "Prazo de entrega" input is wired to `updateOrderInfo(orderId, {...})`; client fields are a separate local draft (see `ClientFields`/`clientDraft` above); Vendedor is still unwired (out of scope for this pass).
- **"Finalizar Pedido"** (`handleFinalizeOrder` in `NewOrder`, bottom of the page, `.finalize-order` in `src/styles/forms.css`) validates `clientDraft.personName`/`.document`/`.phone` and at least one product, then resolves/creates the client, attaches `clientId`, calls `finalizeOrder(orderId)`, and navigates to `/pedidos/{orderId}`. Until this is clicked, the order stays a draft (`isDraft: true`) and is invisible on `Orders`/`Production` — this is what stops a half-filled or abandoned Novo Pedido session from cluttering the rest of the app. If the vendedora navigates away without finalizing, the draft order is simply left behind in memory (harmless — it disappears on reload, same as everything else without a backend); nothing currently cleans it up early, and nobody has asked for that.
- **`OrderDetails` reads the real order from the route**, via `useParams()` → `id` → `orders.find(o => o.id === id)`, instead of a hardcoded "PED-2026-0001". If the id doesn't match any order, it renders "Pedido não encontrado." — this can happen since orders created in one session don't persist past a reload.
- **`Orders` (the list) and `Production` (the Kanban) both read from `useOrders()` too** — `Orders` maps `orders` directly; `Production` flattens every order's `products` into one list (tagging each with `orderId`) via `orders.flatMap(...)`, same shape it used to fake locally.
- **Adding a product is a 2-step wizard inside one `Modal`** (`src/components/ui/Modal.jsx`), driven by `useProductList`'s `addStep: 'info' | 'operations'`: step `'info'` collects tipo/modelo/cor/tecido/quantidade/observações; clicking "Próximo" validates (tipo + quantidade required) and advances to step `'operations'`, which shows `OperationsChecklist`; "Voltar" returns to `'info'` without losing what was typed, "Salvar" creates the product with both the info *and* the chosen workflow at once. This is one continuous modal, not two — the wizard step only changes its *content* and title. There is no gate on this: operations are selectable immediately, at creation time (see domain model above).
- **Editing an existing product's workflow later is a separate, second `Modal`** (`isEditModalOpen`/`openEditModal`/`closeEditModal` in the hook), opened via the `ProductCard`'s "Editar" button — same `OperationsChecklist`, but only touches `workflow`, not the other fields. Always available, no gate.
- **`Production` (`/producao`) is a per-operation Kanban board**, not a per-order/per-product view: a `.tabs` row (reusing the pre-existing, previously-unused `.tabs`/`.tabs button` classes from `App.css`) lets you filter to one operation (Corte, Costura, Bordado, ...); within that operation, three columns (`Pendente`/`Em andamento`/`Concluído`, `src/styles/production.css`'s `.kanban-board`/`.kanban-column`/`.kanban-card`) list every product across **all real orders in the shared store** that has that step. This is the only place in the app where `status` actually changes — everywhere else it's just set to `'pending'` on creation.
- **Status moves both forward and backward** (`moveProductStepStatus(orderId, productId, step, 'forward' | 'backward')` in `OrdersProvider`, via `getNextStatus`/`getPreviousStatus`): the Kanban card's own "Voltar"/"Iniciar"/"Concluir" buttons only affect the currently-selected operation. Clicking a product's name opens a detail `Modal` showing **all** of that product's operations at once (not just the selected tab), each independently steppable forward/backward — this is how you reopen an *earlier* operation (e.g. redo Costura after a defect is found during Bordado) without switching tabs. **Completing one operation never auto-affects any other operation's status** — but starting one *can* now be blocked by the sequence-position gate described in the domain model above (added 2026-07-06); once a step has left `'pending'`, nothing about other steps affects it further.
- **A product's design work is tracked by `product.designStatus`** (`NULL` = not in the design queue, else `'pendente' | 'em_design' | 'aprovacao' | 'concluido'` — item 3.1, 2026-07-10, migrations `0002`/`0003`): the columns of the `/design` kanban, in that order (`'aprovacao'` = layout sent to the client; named that in the *product* flow even though an order stage is also called Aprovação — Pablo's requested column name). **Two entry paths, distinguished by `products.design_is_rework`** (`designIsRework` in the API): the *normal flow* (order advances Venda→Design → every product with `design_status IS NULL` auto-enters as `'pendente'`, `is_rework = false` — trigger inside `PATCH /orders/:id/advance-stage`, same transaction; **a product added to an order that has already left `'venda'` is likewise born `'pendente'`**, whatever stage the order is in — `entersDesignQueue` in `backend/src/routes/orderProducts.js`) and *real rework* (the "Retrabalho de design" checkbox in Produção → `'pendente'` with `is_rework = true`, via its own `PATCH /products/:id/design-rework`). **`needsDesignRework` is derived as "active rework"**: in queue (not `'concluido'`) AND `design_is_rework` — so the rework badges (Orders, Produção, and inside `/design` cards) only light up for genuine client-requested rework, never for normal design flow; the checkbox reflects/controls only the rework marker. Unchecking clears the flag; it only removes the product from the queue if still `'pendente'` (in-progress cards stay, just lose the badge) — confirmed with Pablo. **Second trigger, the reverse direction (remapped 2026-07-11 — Pablo's explicit spec after spotting the old mapping was stale)**: design-kanban moves push the order stage along, evaluated as two *state-based* checks (not transition-based) run in sequence after any design-status change (inside `PATCH /products/:id/design-status`, same transaction): (1) order in `'design'` + every product at `'aprovacao'`-or-beyond → stage becomes `'aprovacao'`; (2) order in `'aprovacao'` + every product `'concluido'` → stage becomes `'producao'`. Running both in sequence covers the skip case (everything already `'concluido'` while still in `'design'` advances twice, straight to `'producao'` — only reachable via direct API, the kanban moves one column at a time). A `NULL` `design_status` blocks both checks (product not in the queue = not accounted for). The response carries `orderStage` so the front updates without refetch — same bolt-on pattern as `orderTotalValue`. Rework completion never touches stage (the stage guards hold: a typical rework's order is already `'producao'`); "Reabrir"/backward moves never regress stage (there is simply no UPDATE in that direction). **This means Aprovação→Produção is now automatic too** — `'producao'` is no longer a manually-clicked "client approved" milestone; the manual "Avançar etapa" only remains truly manual for Venda→Design (plus the anti-stuck re-enable described in the tracker rework below). Every transition is logged to `product_events` with `payload.trigger` (`'order-stage'` | `'manual'` | `'rework-checkbox'`), plus `design_rework_flagged`/`_unflagged` events — the seed of item 3.3's history.
  - **The "product added later" entry path was widened from `stage === 'design'` to `stage !== 'venda'` on 2026-07-25, after Pablo hit the gap in real use.** The original test was too narrow *because of the very automation described above*: the design-kanban triggers move the order stage on their own, so by the time someone adds a product the order has often already slid to `'aprovacao'` or `'producao'` — and in those two cases the new product was born with `design_status = NULL`, i.e. **invisible to design, with nothing anywhere to signal it**. Pablo's workaround was to regress the order to Venda and advance it again, which worked only because the Venda→Design trigger sweeps every product still `NULL`. A product added after the sale always needs artwork (the designer has never seen that piece), so the queue entry now applies at every stage past Venda. **Two deliberate non-changes, confirmed with Pablo**: the order stage does *not* regress (other products may genuinely be in production; the system never auto-regresses stage anywhere else either), and the product enters as normal flow, *not* `is_rework` (the rework badge means "client asked to redo existing artwork" — reusing it for a brand-new product would blur two different signals). The freio that keeps this coherent costs no new rule: an order in `'aprovacao'` already only auto-advances to `'producao'` when *every* product is `'concluido'`, so a newly added `'pendente'` product holds the order back by itself. Verified across all four stages plus that freio (10 API checks) and through the browser on Pablo's exact path (7 checks).
- **That same `.rework-badge` also shows on `Orders`**, on any order card where `order.products.some(p => p.needsDesignRework)` — an interim visibility fix (2026-07-03) since there's no design-specific queue/role yet for someone to actually be routed to. This is a stopgap, not the real fix: it just makes the flag visible somewhere a human might glance at it, without any notification or routing. **The design queue this was waiting for now exists** (`/design`, item 3.1 — no per-sector roles yet, so it's just another screen anyone can open, like Produção); the badge on Orders stays as extra visibility, no longer the only surfacing of the flag.
- **Styling**: global styles/resets in `src/styles/variables.css` and `src/styles/global.css`; each feature area (`orders.css`, `dashboard.css`, `sidebar.css`, `forms.css`, `buttons.css`, `layout.css`, `workflow.css`, `products.css`) has its own file, all imported centrally via `index.css`. `App.css` no longer exists — every rule it had was either moved into the matching feature file or dropped if genuinely dead (see "Fechamentos rápidos" item 2.2). New styles go straight into the relevant feature file. Follow the existing plain-class naming style (e.g. `product-card`, `dashboard-card`, `stage completed`).
- **State management**: shared app data (orders + their nested products) lives in `OrdersProvider`'s React Context, wrapping the whole router — this is what lets `NewOrder`, `OrderDetails`, `Orders`, and `Production` all see the same data instead of each having its own copy. Purely UI-local state (which modal is open, a form draft, which tab is selected) is still plain `useState` per component/hook — don't move that into the context, only shared *data* belongs there. **As of the backend migration's step 5 (2026-07-06), this Context is a client-side cache of the real Postgres database, not the source of truth** — `OrdersProvider`/`ClientsProvider`/`OperationsProvider` fetch from the backend API on mount and persist every mutation through it (see "Backend migration roadmap" below), so a page reload now re-fetches the same data instead of resetting to seed data. The frontend and backend are still separate dev processes though — running just `npm run dev` in the repo root is no longer a fully self-contained loop; the backend (and Postgres) must also be running.

## Backend migration roadmap (started 2026-07-04)

TexFlow is moving from an in-memory Context-only prototype to a real client-server app. **Why**: it will soon be used by multiple people on different computers at Kavi (a vendedora creating pedidos, produção tracking them) — in-memory/Context state doesn't survive across machines or even across a single reload, which no longer fits real multi-user use.

**Decided stack**: Node.js + Express backend (same language as the frontend, chosen partly for learning continuity), PostgreSQL database, Railway for hosting (backend + DB together) once deployed. The existing React frontend is kept as-is architecturally — `OrdersProvider`, `ClientsProvider`, and `OperationsProvider` will be rewritten internally to fetch/persist through a REST API instead of local `useState`, but should keep exposing roughly the same shape of data/functions to the rest of the app, so pages/hooks/components need minimal changes.

**Steps** (steps 1-6 are done — the whole app is deployed and live; don't assume step 7 exists):
1. **Database schema design** — ✅ done, 2026-07-04. Full DDL lives in `backend/src/db/schema.sql`. Six tables: `clients`, `orders`, `products`, `product_workflow_steps`, `product_comments`, `operations`, mapping directly onto the domain model already documented above. Notable decisions (also commented in `schema.sql` itself): `orders` has a numeric `id` PK plus a separate `order_number` (the "PED-2026-0001" string) with its own `UNIQUE` — chosen over using the string itself as PK, for join/index efficiency and to decouple internal identity from the display code; `stage`/`status` columns are `TEXT` + `CHECK` rather than native Postgres `ENUM`s (ENUMs are painful to extend later — no simple transactional `ALTER TYPE ... ADD VALUE`); `product_workflow_steps.step_name` is free text with **no FK to `operations`** — the "outra operação" custom entry in `OperationsChecklist` doesn't require existing in the managed catalog, and a FK here would break that already-validated behavior. Extra indexes beyond what `UNIQUE`/PK constraints auto-create (e.g. on `orders.client_id`, `products.order_id`) were explicitly deferred to step 2, not forgotten.
2. **Backend project setup** — ✅ done, 2026-07-04. `backend/` (sibling to `src/`, same repo) is a Node + Express project: `package.json` (`"type": "module"`, ESM throughout, matching the frontend's module style), `src/server.js` (entry point — reads `PORT`, calls `app.listen`), `src/app.js` (builds the Express app: `cors()`, `express.json()`, and a `GET /health` route), `src/db/pool.js` (a `pg.Pool` reading `DATABASE_URL`), `src/db/schema.sql`. `cors()` is there from the start because the frontend (`localhost:5173`) and backend (`localhost:3333`) are different origins — without it, the browser blocks the requests step 5 will make. **Non-obvious gotcha preserved as a comment in `pool.js`**: ES module imports fully evaluate before the importing file's own top-level code runs, so `dotenv.config()` has to be called inside `pool.js` itself (not just once in `server.js`) — otherwise `DATABASE_URL` would be `undefined` when the `Pool` is constructed. `GET /health` doesn't just check Express is up — it runs `SELECT 1` against the real DB and reports `{ status: 'degraded', database: 'unavailable' }` (HTTP 503) if that fails, so it actually proves the whole scaffold (server + DB) works, not just the server alone. Locally verified end-to-end 2026-07-04: PostgreSQL 16 installed via Homebrew, `texflow` database created, `schema.sql` applied (all 6 tables present), backend's `.env` pointed at it, `curl localhost:3333/health` returned `{"status":"ok","database":"connected"}`. `backend/.env` (real local credentials) is gitignored via the root `.gitignore`'s new `.env` entry — only `.env.example` is committed. **The frontend's `eslint.config.js` now ignores `backend`** — its `globals.browser` config doesn't know Node globals like `process`, so without the exclusion it errors on every backend file with `'process' is not defined`. The backend has no linting of its own yet — not set up, don't assume it exists.
3. **Orders/Products API** — ✅ done, 2026-07-05 (list/create/edit/advance-workflow routes). Three route files: `backend/src/routes/orders.js` (`GET /orders`, `GET /orders/:id`, `POST /orders`, `PATCH /orders/:id`, `PATCH /orders/:id/finalize`, `PATCH /orders/:id/advance-stage`), `backend/src/routes/orderProducts.js` (`POST /orders/:orderId/products`, mounted separately with its own `Router({ mergeParams: true })` so it isn't also reachable at bare `/products`), `backend/src/routes/products.js` (`PATCH /products/:id`, `DELETE /products/:id`, `PUT /products/:id/workflow`, `PATCH /products/:id/workflow/:step`). Shared logic lives in `backend/src/db/ordersQueries.js`: `mapOrder`/`mapProduct` translate DB snake_case (`client_id`, `needs_design_rework`) to the camelCase shape the frontend already uses; `fetchOrders` does 3 plain queries (orders, then their products, then those products' workflow steps) and groups them in JS into the same nested `order.products[].workflow[]` shape the frontend already expects, instead of a SQL-side `json_agg`; `ORDER_STAGES`/`getNextStatus`/`getPreviousStatus` are **duplicated from** (not imported from) `src/data/orderStages.js`/`OrdersProvider.jsx`, since the backend is a separate Node process — keep both in sync by hand if the stage order or status transitions ever change. `backend/src/db/withTransaction.js` wraps a `pool.connect()` client in `BEGIN`/`COMMIT`/`ROLLBACK` for anything that needs more than one write to succeed or fail together: creating an order (insert with a placeholder `order_number`, then `UPDATE` it to `PED-{year}-{id padded}` once the real id is known from `RETURNING`), creating a product with its initial chosen operations (all inserted as `status: 'pending'` — choosing operations is sales-time, only their status is production-time, see domain model), and `PUT /products/:id/workflow`'s diff (steps still selected keep their existing status untouched; newly-selected steps insert as `pending`; deselected steps are deleted) — this is the backend equivalent of `saveWorkflow` in `useProductList.js`, preserving progress across an edit rather than resetting it. `backend/src/utils/asyncHandler.js` exists because Express 4 (the version installed) doesn't catch a rejected promise thrown inside an `async` route handler on its own — every route is wrapped in it, and `app.js` now ends with a 4-arg error-handling middleware that turns any uncaught error into a `500`. Manually verified end-to-end 2026-07-05 against the real local Postgres DB: created a draft order, added a product with two operations, advanced one step's status forward twice (`pending → in_progress → done`), then edited the workflow to drop one operation and add another — confirmed the already-`done` step's status survived the edit untouched — then finalized the order, advanced its stage, and deleted the product (cascade-deleted its workflow rows). 404s (`GET`/`POST` on a nonexistent order or product) and the 400 validation on missing `type`/`quantity` were also exercised and behave correctly. At the time step 3 shipped, there were deliberately no routes yet for `product_comments`, `clients`, or `operations` — those came in step 4 (below).
4. **Clients/Operations/Comments API** — ✅ done, 2026-07-05. `backend/src/routes/clients.js` (`GET /clients`, `GET /clients/:id`, `POST /clients`, `POST /clients/find-or-create`), `backend/src/routes/operations.js` (`GET /operations`, `POST /operations`, `DELETE /operations/:id`), `backend/src/routes/productComments.js` (`GET`/`POST /products/:productId/comments`, mounted like `orderProducts.js` with `Router({ mergeParams: true })`). `POST /clients/find-or-create` mirrors `findOrCreateClient` in `ClientsProvider.jsx` exactly: matches only by `document` (never phone — same reasoning already documented above), returns the existing client if found, otherwise creates one; also handles the rare race where two requests both miss the initial lookup and both try to insert the same `document` — the loser catches Postgres's `23505` unique-violation and just re-fetches instead of erroring. `POST /clients` and `POST /operations` both turn that same `23505` into a `409 Conflict` with a plain-language message, instead of the frontend's current client-side `alert()` on duplicate document. **Non-obvious routing decision**: `DELETE /operations/:id` deletes by numeric id, not by name — operation names like "Revisão/Finalização" contain a `/`, which Express would otherwise split into path segments, breaking a name-based route. `GET /operations` returns `[{ id, name }]` (not a plain `string[]` like `OperationsProvider`'s in-memory `operations` state) specifically so each operation has a stable id to delete by; adapting this shape is step 5's job. Comments are also now embedded in the product shape everywhere a product is returned: `mapProduct` (in `ordersQueries.js`) gained a third `commentRows` argument and a `comments` field, `fetchOrders` and `getProductById` both fetch `product_comments` alongside workflow steps — so `GET /orders/:id` now returns each product's full comment history (oldest first; "newest first" stays a `ProductCard`-only display concern via `.slice().reverse()`, exactly like today). Manually verified end-to-end 2026-07-05 against the real local Postgres DB: created a client, hit the duplicate-document paths on both `POST /clients` (409) and `POST /clients/find-or-create` (returns the existing record instead of erroring), created an operation with a slash in its name and deleted it by id, added two comments to a product and confirmed both came back embedded in `GET /orders/:id`, and confirmed `POST /products/:id/comments` 404s for a nonexistent product. **Not built yet**: no `PATCH`/`DELETE` on clients (nothing in the frontend needs them yet), no way to edit an operation's name (only add/remove, matching `OperationsProvider`'s current capabilities).
5. **Connect the frontend to the API** — ✅ done, 2026-07-06. `OrdersProvider.jsx`, `ClientsProvider.jsx`, and `OperationsProvider.jsx` no longer seed from `src/data/*.js` — they fetch from the backend on mount and persist every mutation through it. `src/services/api.js` (new) is a thin fetch client: one `request()` helper (base URL from `VITE_API_URL`, default `http://localhost:3333`; throws a friendly "servidor não respondeu" `Error` if the fetch itself fails, e.g. backend down) plus `ordersApi`/`productsApi`/`commentsApi`/`clientsApi`/`operationsApi` objects mirroring the routes built in steps 3-4 one-to-one. `.env.example` (frontend root) documents `VITE_API_URL`; a real `.env` is optional locally since the default already points at the local backend.
   - **Every mutator is now `async` and follows one contract**: on success it returns the created/updated resource (or, for `createOrder`/`findOrCreateClient`, just the id — matching what callers actually needed before); on failure it `alert()`s the server's error message itself and returns `null`. This means pages don't need their own `try/catch` — they just do `const result = await someMutator(...); if (!result) return` before continuing (closing a modal, navigating, clearing a draft). Every call site that used to be a bare synchronous call (`NewOrder`'s `handleFinalizeOrder`, `useProductList`'s `saveNewProduct`/`saveWorkflow`/`addComment`, `Clients`' `saveClient`, `Settings`' `handleAddOperation`) was updated to `await` and check this return value; fire-and-forget calls with nothing sequenced after them (`Production`'s `moveProductStepStatus`/`toggleProductDesignRework`, `Settings`'/`Production`'s `removeOperation`) didn't need any change at their call site.
   - **`OperationsProvider` keeps an internal `{id, name}` list but still exposes `operations` as a plain `string[]`** (derived via `.map(o => o.name)`) — so `Settings`, `Production`, and `OperationsChecklist` needed zero changes for the operations part. `removeOperation(name)` looks the matching `id` up internally before calling `DELETE /operations/:id`.

### Item 6 — Esqueci minha senha — ✅ done, 2026-07-30 — **fecha o roadmap**

Os usuários da Kavi não têm e-mail cadastrado, então não existe reset por link: a pessoa registra um pedido pela tela de login e um admin aprova dentro do próprio sistema. Migration `0010`.

- **`POST /auth/password-reset-request` é a única rota pública além do login e do `/health`** — e tem que ser: quem esqueceu a senha não consegue se autenticar para pedir. Fica em `auth.js` porque é o único router montado **antes** do `requireAuth`.
- **Anti-enumeração**: responde sempre a mesma mensagem de sucesso, exista o usuário ou não — mesma convenção que o login já usava para não revelar quais usernames existem.
- **Índice UNIQUE parcial** (`WHERE status = 'pendente'`): no máximo um pedido pendente por usuário, quantos resolvidos quiserem. Sem ele, cinco cliques em "esqueci minha senha" virariam cinco linhas na fila do admin — e a rota é pública, então nem precisa de má intenção. Verificado: 3 cliques = 1 pedido.
- **Ordem das rotas importou**: `/users/password-reset-requests` precisa ser declarada **antes** de `/users/:id`, senão o Express lê o caminho como um id. Mesma armadilha já registrada no `App.jsx` (`/pedidos/novo` antes de `/pedidos/:id`).
- **Aprovar devolve a senha para `kavi2026`** (decisão do Pablo, mantida depois de eu levantar que isso deixa a conta com uma senha conhecida até a troca; o raciocínio dele é que a pessoa troca no primeiro acesso). A troca de senha e o fechamento do pedido acontecem **na mesma transação**. A resposta devolve a senha padrão para a tela mostrá-la a quem aprovou — é o admin que avisa a pessoa. **O sistema NÃO obriga a troca no primeiro acesso**; não existe esse mecanismo, depende de a pessoa ir em Minha Senha.

Agora o conceito mora em `src/data/orderStages.js`, que já era o dono do vocabulário de estágios:

- `FINAL_STAGE` (`'entregue'`), `isActiveOrder(order)` (não é rascunho e não foi entregue) e `isInWorkflow(order)` (ativo **e** já fora da Venda — o recorte das telas de trabalho).

**Os dois buracos que existiam:**
- **Fila de `/design`** filtrava só `!isDraft`. Como todo produto de um pedido entregue está com `designStatus = 'concluido'`, ele ficava parado na coluna "Concluído" **para sempre**. - **`GET /reports/bottlenecks`** usava `stage != 'venda'`, que **inclui** `'entregue'`. Agora é `stage NOT IN ('venda', 'entregue')` nas duas queries (`volumeByStep` e `stuckProducts`).
  - **Correção de registro, importante para não repetir o raciocínio errado**: a justificativa original que dei era "um pedido entregue com uma Costura que ninguém marcou como concluída". **Isso é bem mais difícil de acontecer do que parece** — o gate de sequência impede que as etapas de Conferência *comecem* antes de as de fabricação concluírem, e a trava de entrega exige as de Conferência concluídas. Ou seja, o caminho ingênuo é bloqueado (confirmado empiricamente: `409 "Não é possível iniciar Revisão/Finalização antes de concluir: Costura, Bordado, Corte"`). O filtro continua certo — só é menos frequente do que a justificativa original sugeria.
- **`GET /reports/avg-time-per-step` NÃO foi filtrado, de propósito**: tempo médio é justamente estatística histórica; excluir o que já foi entregue destruiria a base de cálculo. Gargalo é problema de hoje; média é memória.

Conforme os anos de Kavi acumularem entregas, cada carregamento vai baixar o histórico inteiro — é isso que um dia vai forçar paginação ou filtro no servidor. Não resolvido preventivamente.

### Relatório de prazo real venda → entrega (✅ 2026-07-30)

`GET /reports/lead-time` + uma seção nova no topo de `Relatórios`. Só existe porque a migration `0009` passou a carimbar `orders.picked_up_at` (item 1 do roadmap de produção) — é a primeira coisa a consumir esse dado.

- **Marco inicial: `orders.created_at`.** A escolha óbvia seria o evento `order_finalized` (o clique em "Finalizar Pedido"), semanticamente mais preciso — **mas o banco de produção tem ZERO desses eventos**: o evento só passou a ser gravado no item 3.3 (18/07) e nenhum pedido foi finalizado pela tela desde então, então o relatório sairia vazio. **Distorção conhecida e escrita na própria tela**: `created_at` é quando a vendedora abriu "Novo Pedido" (a tela cria o rascunho na montagem); se ela abrir e só finalizar dias depois, a contagem começa cedo demais. Na prática é a mesma sessão, e o desvio é pequeno perto de um ciclo de semanas. **Um `COALESCE` do evento com o `created_at` foi descartado de propósito** — daria uma média com dois significados diferentes dentro dela, pior que um proxy consistente. Se um dia houver volume de `order_finalized`, aí sim vale reavaliar (e migrar a métrica inteira, não misturar).
- **Duas medidas, porque prazo real sozinho é número sem referência**: quanto levou (`picked_up_at::date - created_at::date`) e se cumpriu o prometido (`picked_up_at::date - deadline`, positivo = atraso, negativo = adiantado, `NULL` = pedido sem prazo definido). Quem não tem `deadline` entra na primeira e fica fora da segunda — daí o resumo mostrar "1 de 2" e avisar quantos ficaram sem prazo, senão o denominador confundiria.
- **Subtração de `::date`, não de `timestamp`**: a pergunta é "quantos dias" do jeito que uma pessoa conta, não frações de hora.
- **Duas queries** (agregado sobre todos os entregues + as últimas 20 linhas para a tabela), mesmo formato de `bottlenecks`. O resumo continua correto quando houver centenas de entregas, sem mandar todas pela rede.
- **A API devolve `clientId` cru, não o nome montado no SQL** — `getClientDisplayName` (`src/data/clients.js`) é o único lugar que decide o que exibir de um cliente, e replicar aquele `COALESCE` na query criaria um segundo dono da mesma regra. A página passou a usar `useClients()`, que já busca a lista na montagem para todos os papéis.
- **Sem filtro de período**, igual aos dois relatórios que já existiam. Quando o volume justificar, é aí que se pensa em recorte de datas.
- **`avg-time-per-step` continua SEM filtrar entregues** (ao contrário de `bottlenecks`): média é memória, gargalo é problema de hoje.
- **Correção de localização feita junto**: `formatHours` usava `toFixed(1)`, que produz `"23.3 dias"` — ponto, não vírgula, num app inteiramente em português. Virou `toLocaleString('pt-BR')` via o helper `decimal()`, que a seção nova também usa. Afeta as duas tabelas que já existiam (é só exibição). `formatDays` mostra inteiro sem casa decimal ("20 dias", não "20,0 dias") e só a média, que raramente é redonda, com uma casa.
- **Verificação**: 22 checks de API — três cenários montados de propósito (**atrasado**, **adiantado** e **sem prazo**, com `created_at` retrodatado por SQL, já que a API não deixa escolher a data de criação), com **todo o resumo conferido contra a mesma agregação rodada em SQL cru** em vez de valores chumbados no teste; mais ordenação, limite de 20, rascunho ficando de fora e `clientId` cru. E 28 no navegador (desktop e 390px), incluindo os três selos de cumprimento, a tabela rolando no próprio contêiner no celular e zero erro de console. Dois defeitos só apareceram ao **olhar** a captura, não nas asserções: o "20.8" com ponto e uma frase torta na nota de rodapé.

**Como conferir/limpar de novo** (o roteiro, já que não existe rota de delete no app): listar `cloudinary.api.resources()` para `image`/`raw`/`video` (paginando por `next_cursor`), extrair o `public_id` de cada `product_files.file_url` com `/upload/(?:v\d+/)?(.+?)(?:\.ext)?$`, e apagar a diferença com `cloudinary.api.delete_resources(lote, { resource_type })` em lotes de 100. **Reconferir contra o banco no momento de apagar**, não só no inventário — um arquivo enviado no meio do caminho não pode morrer por estar fora de uma lista velha. A API `cloudinary.api.usage()` **demora a refletir** a limpeza (o consumo é recalculado periodicamente), então não estranhe se logo depois ela ainda mostrar os números antigos.

## Cobrança do saldo na retirada (✅ 2026-07-31)

Clicar em **"Registrar retirada"** com saldo em aberto passa a avisar quanto falta e abrir o modal de pagamento **antes** de fechar o pedido — a retirada é o último momento em que o cliente está na loja. Frontend puro: **nenhuma rota, coluna ou validação nova no servidor**, e isso é coerente, não preguiça (ver abaixo).

- **É aviso, não trava — decisão do Pablo.** Cancelar e clicar de novo entrega **com saldo devedor**. A Kavi fia para cliente conhecido; bloquear deixaria quem está no caixa sem saída a não ser **lançar como pago o que não recebeu**, corrompendo justamente o dado que a trava queria proteger. Por isso **não existe 409 no servidor** para este caso, ao contrário da trava de conferência pendente (item 1 do roadmap de produção): lá a regra é "não pode", aqui é "veja isto antes" — pôr um gate no servidor contradiria a decisão de produto.
- **`pickupWarned` (estado local de `OrderDetails`) é o que faz o aviso ser aviso**: avisa **uma vez por visita à tela**. Some no reload/navegação, e é isso mesmo — o objetivo é interromper o gesto uma vez, não perseguir a pessoa.
- **Quitar dentro do modal fecha o pedido na sequência**, sem segundo clique (`confirmPayment` chama `advanceOrderStage` quando `amountPaid >= totalValue` **e** o modal foi aberto pela retirada) — evita receber o dinheiro e esquecer o pedido aberto. **Pagamento parcial não fecha nada**: só registra o valor.

## Development philosophy

These principles were explicitly agreed on with the user and should guide new work, not just the existing code:

1. Model the system after the confecção's real process — don't bend the process to fit software limitations (e.g. don't force a single fixed pipeline onto all products).
2. Think architecture and reuse before implementation.
3. Extract a reusable component whenever it makes sense — check `components/ui` before inlining new markup.
4. Avoid duplicating logic/markup (DRY).
5. Keep the structure scalable and consistent with conventional professional React apps (pages-as-folders, ui/layout split, per-feature CSS).
6. Keep responsibilities separated: components, pages, styles, data, and (future) services/hooks each in their own place.

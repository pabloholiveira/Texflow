# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

TexFlow (package name `sistema-confeccao`) is a front-end-first prototype, evolving into a real client-server app, for managing the production workflow of a garment manufacturer ("confecção") called **Kavi**, from sale to delivery. UI copy and domain terms are in Portuguese (pedidos, clientes, produção, etc.) — keep new UI text consistent with that. Data lives in a real Node/Express + PostgreSQL backend (`backend/`) as of the backend migration's step 5 (2026-07-06) — React Context Providers (`src/context/`) now fetch from and persist through that API instead of seeding in-memory from `src/data/*.js`. This backend was built specifically because Kavi will have multiple people (vendedora, produção) using the system from different computers — see "Backend migration roadmap" below for what's done and what's still ahead (deploy, auth/roles).

**TexFlow is explicitly NOT a full ERP.** It is not a financial system and not a fiscal/invoicing system. Its sole focus is controlling production flow: registering orders, tracking each product through its stages, surfacing bottlenecks, and organizing files/comments/history per product. Do not add invoicing, accounting, or tax-related scope unless the user asks.

## Lições de método (leia antes de verificar, refatorar ou culpar o código)

Quatro lições que já se repetiram neste projeto e custaram tempo real. Estão consolidadas aqui e referenciadas nos lugares onde aconteceram.

1. **Verifique o bug pelo caminho que um humano percorreria, antes de documentá-lo como bug.** A automação fabrica os próprios defeitos: um `page.goto()` logo após o login abortou requisições em voo e virou "bug do `request()`" (item 3.2); um teste que recarregava `/pedidos/novo` — página que cria um rascunho novo a cada montagem — virou "a grade de tamanhos não persiste"; um "Reabrir não volta pra Aprovação" era expectativa minha errada sobre o botão. **E "reproduz sem as minhas mudanças" prova apenas que a causa não é a mudança — não prova que a causa está no app**: um script defeituoso reproduz igual em qualquer versão do código.

2. **Ao renomear ou extrair um campo já consumido em vários pontos, dê `grep` pelo nome ANTIGO antes de fechar o item.** Atualizar só as ocorrências que aparecem no diff da mudança principal não basta, e **nada acusa**: ler propriedade inexistente em JS devolve `undefined`, não erro, então o lint passa. Foi assim que `column.status` → `column.value` sumiu com **todos** os botões do kanban de `/design`, deixando a fila só-leitura por meses.

3. **A verificação precisa cobrir o que a mudança DESLOCOU, não só o que ela criou.** Verificar a feature nova não cobre a tela que a refatoração mexeu de passagem. (A extração acima mexeu na página `Design`, que não entrou na verificação; e a primeira rodada dos `<label>` pulou justamente o modal de arquivos, o bloco mais refatorado.)

4. **Olhe a captura de tela; não confie só na asserção passando.** Vários defeitos reais só apareceram no olho, com as medições passando: a coluna "OK" da ficha impressa ocupando um terço da folha, o `20.8` com ponto num app inteiramente em português, a tabela espremida quebrando "PED-2026-0003" em três linhas, a nota de rodapé torta.

Corolários que também já custaram tempo:
- **Tempo fixo (`waitForTimeout`) em teste contra produção é fonte de falso negativo** — espere pelo elemento (`waitFor`), não pelo relógio.
- **Ao comparar moeda formatada em teste, normalize o espaço**: `toLocaleString('pt-BR')` separa `R$` do número com espaço **não-quebrável** (U+00A0), que não casa com espaço comum.
- **Antes de suspeitar do app, confira se o estado de teste é o esperado**: kanban vazio porque o pedido estava em `'venda'`, aba padrão sem produto porque a Lavagem é opcional, `409` que era o gate de sequência funcionando corretamente.

## Domain model (read before touching order/product/production logic)

This is the most important — and least obvious from the code alone — part of the architecture. It was worked out deliberately with the user and should not be re-litigated without their input.

- **An order (`pedido`) contains multiple products (`produtos`).** E.g. order 125 = 80 t-shirts + 30 caps + 20 polos, all one order.
- **Three stages belong to the order as a whole, happen once, and are shared by every product in it**: Venda (sale) → Design → Aprovação (approval).
- **After approval, each product follows its own independent workflow.** Tracking/status must be done per-product, not per-order. Different products in the same order can be in completely different stages at the same time (e.g. the t-shirt is in Costura while the cap is already in Bordado).
- **Workflow per product is chosen manually, per product, from a configurable operations list** — it is not one fixed pipeline and not auto-inferred from product type. Example variations:
  - Camiseta: Costura → Silk → Revisão/Finalização
  - Boné: Bordado → Embalagem
  - Camisa Polo: Costura → Bordado → Revisão/Finalização
- **Available operations**: `src/data/operations.js`'s `DEFAULT_OPERATIONS` (Corte, Costura, Bordado, Silk, DTF, Lavagem, Revisão/Finalização, Embalagem) is only the **seed** list now — the live, editable list lives in `OperationsProvider`'s context (`src/context/`), managed from the `Settings` screen (2026-07-03). The product form also accepts a free-text "outra operação" for one-off steps not in the list — those get folded into the same selection, not stored separately.
- **Bordado (embroidery), Silk (screen printing), and DTF (direct-to-film printing) are independent operations** — a product can need any combination of them, or none; they do not depend on each other. (Earlier discussion called this generically "Estampa" — Silk/DTF is the more precise, current vocabulary; don't reintroduce a generic "Estampa" field.)
- **Operations have a production sequence, modeled as layered "positions" (✅ built, 2026-07-06), not a single linear order.** Each operation in the catalog (`operations.sequence_position`, an integer) sits at a layer; an operation can only start (`status` leaving `'pending'`) once every *other selected operation on that same product* with a strictly lower position is `'done'` — operations sharing the same position are independent of each other and don't gate one another. Current layout: `1` Corte → `2` Bordado/Silk/DTF/Costura (siblings — Costura does **not** wait on Bordado/Silk/DTF, only on Corte, because their relative order can vary job to job) → `3` Revisão/Finalização (waits for all *selected* position-1 and position-2 steps) → `4` Lavagem → `5` Embalagem. **The gate only blocks the start of a step** — once a step leaves `'pending'`, it can move freely (including back to an earlier status) regardless of what happens to other steps afterward; this was a deliberate simplification over gating every forward transition. A custom "outra operação" step with no matching row in the `operations` catalog (or a catalog row with `sequence_position = NULL`) is exempt on both sides: it's never blocked, and it never blocks anything else. Enforced server-side only, in `PATCH /products/:id/workflow/:step` (`backend/src/routes/products.js`, via `findBlockingSteps` in `backend/src/db/ordersQueries.js`) — rejects with `409` and a message naming the still-pending steps. **No frontend gating/disabling was added** (e.g. graying out "Iniciar" before the fact) — clicking it just surfaces the 409's message via the existing `alert()`-on-failure pattern already used everywhere else; proactive UI polish here was deliberately skipped, consistent with "Visual polish (intentionally deferred)" below. Positions aren't exposed as configurable-via-drag-and-drop; `Settings` just gained a plain numeric "Posição (opcional)" input next to the existing add-operation text field, so **new** operations can be slotted in immediately — reordering the *existing* ones still means editing the position number by hand (no bulk reorder UI).
- **Placement of embroidery/print (frente, costas, manga direita/esquerda, combinations, etc.) is deliberately NOT modeled as structured fields.** It's a single free-text observations field (e.g. "Bordado no peito esquerdo", "Silk frente e manga"). This was a conscious simplification — do not "improve" it into separate location/side/position fields without the user asking.
- **A product's workflow is stored as `product.workflow: [{ step, status }]`**, where `status` is `'pending' | 'in_progress' | 'done'`. Selecting/deselecting operations only changes which steps exist in the array; re-editing a product must preserve the `status` of steps that survive the edit (don't reset progress just because the operations were touched again) — see `saveWorkflow` in `src/hooks/useProductList.js`.
- **Choosing *which* operations a product needs is a sales-time decision, not a production-time one.** The vendedora already knows this when taking the order — the client is the one asking for "bordado no peito" or "silk nas costas" — so it must be selectable immediately when a product is created, with no gate tied to `order.stage`. What legitimately *can't* happen before the order reaches `'producao'` is a chosen operation's `status` advancing from `pending` to `in_progress`/`done` — that's physical work starting, which needs the approved artwork. **Don't reintroduce a gate on selecting operations** (an earlier version of this app briefly did, and it was wrong — see "Important nuance" below); if you build the future production board, gate *status advancement* there instead.
- **Per-product entities planned**: tipo, modelo, cor, tecido, quantidade, observações, status, workflow próprio (see above), arquivos próprios (files belong to the product, not the order — arte frente/costas, logo, arquivo de bordado, mockup, manual), comentários internos (built 2026-07-03, see Architecture below — internal-only, never shown to the client), histórico (timestamped event timeline, e.g. "08:00 Costura iniciada", "09:30 Costura finalizada" — still not built, don't confuse with comments; a comment is a free-text note, history would be an automatic log of state changes).
- **Modelo (model) is a distinct, meaningful field** from tipo — e.g. "Camiseta Raglan" vs "Camiseta Tradicional" — plus its own free-text observations for construction details (e.g. "recorte lateral cinza").
- **⚠️ MUDANÇA DE DECISÃO (2026-08-05): o layout aprovado é do PEDIDO, não do produto.** Subir o layout em qualquer produto faz ele valer para todas as peças daquele pedido — é o mesmo arquivo, a mesma linha no banco, não uma cópia. **`'referencia'` não mudou**: continua sendo do produto, porque é material que o cliente entrega para uma peça específica. Ver "Cancelamento de pedido e layout por pedido" adiante para a modelagem. O parágrafo abaixo descreve as duas categorias e continua valendo em tudo o mais (os dois momentos do fluxo, a ausência de gate, o Cloudinary), **menos onde diz que o layout é por produto**.
- **Files have two categories, tied to two different moments in the flow, not one generic "attachments" bucket.** `'referencia'` = material the vendedora receives from the client *at the sale itself* (photos, the client's logo, a fabric-tone reference) — needed by design to build the mockup, so upload must be available immediately at product creation (`NewOrder`'s and `OrderDetails`' add-product wizard, 'info' step), not gated behind any later step. `'layout_aprovado'` = the final approved mockup PDF, consulted afterward by every production sector (costura, bordado, silk, corte, DTF, etc.) as the reference for how the piece should turn out — this only exists after client approval, so it's uploaded later, but **deliberately has no stage gate either** (confirmed with Pablo — same "don't add gates nobody asked for" philosophy as operation selection). Both categories can also be added **after** the product already exists, any time, via a `ProductCard` "Arquivos" button/modal (mirrors the existing "Comentários" modal exactly). Files never touch the app's own server disk — actual bytes go to **Cloudinary** (chosen for its free tier and minimal setup versus S3/R2 at this scale); the DB only stores the resulting URL (`product_files.file_url`).

## Architecture

- **Stack**: React 19 + Vite 8, `react-router-dom` v7 for routing. Plain JSX (`.jsx`, no TypeScript). Vanilla CSS files (one per feature area under `src/styles/`), no CSS modules or CSS-in-JS.
- **Routing** (`src/App.jsx`): a single `BrowserRouter` with all routes declared flatly — `/`, `/login`, `/pedidos`, `/pedidos/novo`, `/pedidos/:id`, `/clientes`, `/design`, `/producao`, `/relatorios`, `/configuracoes`. `/pedidos/novo` is declared **before** `/pedidos/:id` deliberately — this fixed a real bug where "novo" was being swallowed by the `:id` param. Preserve this ordering (specific static routes before dynamic ones) when adding routes.
- **Layout**: every page (except Login) wraps its content in `<Layout>` (`src/components/layout/Layout.jsx`), which renders the `Sidebar` nav plus a `<main className="content">` slot. Follow this convention for any new page.
- **Pages** (`src/pages/*/index.jsx`, not `<Name>.jsx`): deliberate choice over flat files so a growing page can gain siblings (`DashboardCards.jsx`, `dashboard.css`, etc.) without cluttering `pages/`. Historically each page defined its own mock data inline as local arrays/objects, but that's no longer true anywhere — `Dashboard` and `Reports` (both fixed 2026-07-07) were the last two still doing that, and `Login` (fixed 2026-07-06, see the auth step in the backend migration roadmap) was the last unimplemented stub. Every page now reads real data through `useOrders()`/`useClients()`/`useOperations()` or, for `Reports`, its own `reportsApi` calls.
- **`src/data/orders.js`** (`initialOrders`) seeds the shared store below with 3 demo orders (each with real nested products/workflows) — this used to be an empty placeholder. `src/data/clients.js` (`initialClients`, `getClientDisplayName`) likewise seeds the clients store — also no longer an empty placeholder. `products.js` is still an empty placeholder, not yet wired into any page.
- **`src/components/ui/`** vs **`src/components/layout/`**: `ui` holds generic reusable presentational components (`Button`, `Input`, `Card`, `Modal`, `Select`, `Textarea`, `Badge`, `ProductCard`) — chosen over the earlier `components/common` naming to match common React convention. Before building new UI, ask "can this be a reusable component?" — if yes, add it to `ui/` rather than inlining markup in a page. `Textarea` and `Select` are implemented (both mirror `Input`'s prop shape — `Textarea` adds `rows`, `Select` adds `options: [{ value, label }]`), e `FileInput` (2026-07-29) cobre `<input type="file">`, que não cabe no `Input` por ser sempre não-controlado; `Badge` segue como stub vazio.
- **`Button`** takes a `variant` prop (`primary`/`secondary`/`danger`) mapped to a `btn-{variant}` class — follow this pattern for new variants rather than adding one-off className logic.
- **`ProductCard`** is the single reusable representation of a product (icon, modelo, cor, quantidade, status, observações, editar/excluir/comentários actions), reused across Novo Pedido and Detalhes do Pedido (and meant for Produção/Relatórios too) rather than re-implemented per screen. It computes an overall status badge from `product.workflow` (`Não iniciado` / `Em andamento` / `Concluído`) and renders each workflow step as a chip color-coded by that step's own `status` (`workflow-chip-pending|in_progress|done`) — so a product's progress is visible without opening anything else. `.product-card` and its sub-elements went **years of project-time with zero CSS** (a documented, intentional gap) — first real styles landed in the 2026-07-10 polish pass (`src/styles/products.css`); see "Visual polish" below.
- **`src/context/` is the shared front-end cache of the backend for the whole app** (before step 5 of the backend migration it was genuinely the in-memory database; now `OrdersProvider` fetches from and persists through the real API — see "Backend migration roadmap" below) — split into two files on purpose:
  - `ordersContext.js` (plain `.js`, no JSX) exports the raw `createContext()` result and a `useOrders()` hook (`useContext` wrapper). Any page/hook calls `useOrders()` to read `orders` or call a mutator.
  - `OrdersProvider.jsx` owns the actual `orders` array as `useState` (fetched from `GET /orders` on mount, kept in sync by every mutator's response) and exposes all the mutators: `createOrder`, `finalizeOrder`, `updateOrderInfo`, `advanceOrderStage`, `addProduct`, `removeProduct`, `updateProductWorkflow`, `moveProductStepStatus`, `toggleProductDesignRework` — every one of these is now `async`, returning the created/updated resource on success or `null` on failure (after already alerting the error itself). Every order embeds its own `products` array — this mirrors the domain model directly (an order *contains* products, not a parallel list keyed by order id).
  - **Every order created via `createOrder()` starts with `isDraft: true`** (the column's DB default, `backend/src/db/schema.sql`), and only flips to `false` via `finalizeOrder(orderId)`. `Orders` and `Production` both filter out draft orders (`orders.filter(order => !order.isDraft)`) before showing anything. This exists because `NewOrder` creates its order in the shared store the moment the page mounts — without the draft flag, a half-filled or abandoned order would already be visible to everyone else.
  - They're split into two files because of a real ESLint rule (`react-refresh/only-export-components`): a `.jsx` file that exports both a component (`OrdersProvider`) and a non-component (`useOrders`) breaks Vite's Fast Refresh. Keep this split — don't merge them back into one file.
  - `<OrdersProvider>` wraps `<BrowserRouter>` in `src/App.jsx`, so every routed page can call `useOrders()` regardless of where it sits in the route tree.
- **`src/context/clientsContext.js` + `ClientsProvider.jsx`** mirror the same split-file pattern, as a second, independent context — clients are a distinct entity from orders, not a field owned by `OrdersProvider`. `ClientsProvider` owns `clients` (seeded from `src/data/clients.js`) and exposes `addClient(client)` and `findOrCreateClient(clientInfo)`. `<ClientsProvider>` wraps `<OrdersProvider>` in `App.jsx` (nesting order between the two doesn't matter — they don't depend on each other).
- **A client is `{ id, personName, companyName, document, phone, email }`**: `personName`, `document` (CPF/CNPJ), and `phone` are required; `companyName` and `email` are optional. `getClientDisplayName(client)` (`src/data/clients.js`) is the one place that decides what to *show* for a client — company name if present, else the person's name — use it instead of reading `client.companyName`/`client.personName` directly in JSX.
- **An order references a client via `order.clientId`, not a free-text name.** This replaced an earlier `order.client` string field entirely (2026-07-03) — the user asked for orders to cross-reference real client records instead of comparing typed-in names. **Matching is by `document` (CPF/CNPJ) only, not phone** — a deliberate call: phone numbers can be shared (a shared landline, a family), so they're not a safe uniqueness key, while a CPF/CNPJ is. `findOrCreateClient` in `ClientsProvider` looks up by `document`; if no client has that `document` yet, it creates one and returns the new id. Don't change this to match by phone, or by "phone or document" — document is intentionally the sole key.
- **`src/components/ui/ClientFields.jsx`** is the one reusable form (the 5 client fields, wrapped in `.form-grid`) used by `Clients`' "Adicionar Cliente" modal directly, and by `ClientAutocomplete` (below) as its manual-entry fallback — don't duplicate these five `<Input>`s a third time; extend `ClientFields` instead.
- **`src/components/ui/ClientAutocomplete.jsx`** (2026-07-04) wraps `ClientFields` with a search-existing-client step, used in `NewOrder`'s "Informações Gerais": typing into "Buscar cliente existente" filters `clients` by `personName`/`companyName`/`document` (first 5 matches, shown as a plain list below the input — not an absolutely-positioned dropdown, kept simple on purpose); clicking a match calls `onChange(selectedClient)` with the *entire* client record, and the component then shows a compact read-only "cliente selecionado" summary + "Trocar cliente" button instead of the editable fields (this prevents accidentally editing a selected client's `document` and silently detaching the order from the right record). If nothing is selected, `ClientFields` stays visible/editable underneath the search box for registering a brand-new client — exactly the old behavior. **This component owns no server-of-truth logic** — it just bubbles the full client object up via `onChange`; `NewOrder`'s existing `findOrCreateClient(clientDraft)` call at finalize time didn't need to change at all, since a selected existing client's `document` already matches an existing record.
- **`src/components/ui/ProductFields.jsx`** (2026-07-04) extracts the product-info form (tipo/modelo/cor/tecido/quantidade/observações) that used to be duplicated verbatim in both `NewOrder` and `OrderDetails` — both now render `<ProductFields product={product} onChange={handleChange} />` in the add-product modal's `'info'` step. `Modelo`/`Cor`/`Tecido` use `SuggestibleInput` instead of plain `Input`.
- **`src/components/ui/SuggestibleInput.jsx`** is a generic single-field text input with a suggestion dropdown — deliberately **not** the same pattern as `ClientAutocomplete`: it doesn't lock into a "confirmed" state, doesn't replace other fields, and just fills its own `value` on suggestion click, exactly like typing would. `ProductFields` derives each field's suggestions live from every product across every order (`orders.flatMap(order => order.products)`, distinct non-empty values per field via `getDistinctValues`) — there is no separate managed catalog, unlike `DEFAULT_OPERATIONS`/`OperationsProvider`; the user explicitly wants free text with reuse-what-was-typed-before suggestions, not a rigid dropdown. **Gotcha worth preserving**: the suggestion buttons use `onMouseDown` (not `onClick`), and blur hides the list on a `setTimeout` — clicking a suggestion while the input has focus fires blur before a plain `onClick` would register, so `onClick` alone would make suggestions unclickable.
- **`NewOrder` holds client info as a local draft (`clientDraft`), separate from the order itself**, until "Finalizar Pedido" is clicked. Only then does it call `findOrCreateClient(clientDraft)` and attach the resulting id via `updateOrderInfo(orderId, { clientId })`. This mirrors the same "draft, then commit" pattern already used for products — it avoids calling `findOrCreateClient` on every keystroke (which would risk creating a client from a half-typed CPF/CNPJ before the vendedora finishes typing).
- **`Clients` (`/clientes`)** lists every client with a computed order count/history (`orders.filter(order => !order.isDraft && order.clientId === client.id)`) and an "Adicionar Cliente" modal that blocks saving a duplicate `document` with an `alert`. This is a direct client-registration flow — separate from (and not gating) `NewOrder`'s find-or-create path.
- **`src/context/operationsContext.js` + `OperationsProvider.jsx`** are a third, independent context (same split-file pattern) owning the live list of production operations, seeded from `DEFAULT_OPERATIONS`. `Settings` (`/configuracoes`) is now a real page: lists every operation with a "Remover" button, plus an add-new-operation row (reusing `.operation-custom`, the same class `OperationsChecklist`'s "outra operação" row uses). `OperationsChecklist` and `Production`'s `.tabs` row both read from `useOperations()` instead of importing `DEFAULT_OPERATIONS` directly — an operation added in Settings shows up immediately in both places. **Removing an operation doesn't touch any product that already has it selected** — `OperationsChecklist`'s existing `extraSteps` logic (steps in `selectedSteps` but not in the base list) already renders it as a still-checked, no-longer-in-the-base-list option, so this "just worked" without extra code.
- **`src/hooks/useProductList.js`** now takes an `orderId` and reads/writes that order's products **through `useOrders()`** — it no longer owns the products array itself. It still centralizes all the *UI-only* state (which modal is open, the draft form fields, `selectedSteps`) and the add-product wizard / edit-workflow logic, so `NewOrder` and `OrderDetails` share the exact same logic instead of duplicating it. Any future screen that manages a product list should use this hook rather than reimplementing it — just pass it the relevant `orderId`.
- **Per-product internal comments** (`product.comments: [{ id, author, text, createdAt }]`) are a third modal managed by `useProductList` (`isCommentsModalOpen`/`commentingProduct`/`commentDraft`/`openCommentsModal`/`closeCommentsModal`/`addComment`), opened via a "Comentários" button on `ProductCard` (shows a count, e.g. "Comentários (2)", when non-empty). Newest comment shows first (`.slice().reverse()`, doesn't mutate the stored array). `OrdersProvider.addProductComment(orderId, productId, comment)` appends to the array. **`author` is a free-text field the person fills in themselves — there is no login system yet**, so there's no way to know who's actually typing; don't assume this is a real authenticated identity. Once real auth exists, this should auto-fill from the logged-in user instead of being a manual `Input`.
- **Per-product files** (✅ built, 2026-07-06 — see domain model above for the two categories) are a fourth modal, same shape as comments: `isFilesModalOpen`/`filesProduct`/`fileDraft`/`selectedFile`/`openFilesModal`/`closeFilesModal`/`uploadFile` in `useProductList`, opened via a new "Arquivos" button on `ProductCard`. **One real sequencing wrinkle, unlike comments**: a "referência" file can be attached *during the add-product wizard's 'info' step*, before the product exists in the database yet — `referenceFiles` holds raw browser `File` objects in local state (`addReferenceFile`/`removeReferenceFile`), and `saveNewProduct` only actually uploads them (looping over `referenceFiles`, one `addProductFile` call each) *after* `addProductToOrder` succeeds and returns the product's real id; nothing is uploaded if product creation itself fails. Backend: `backend/src/services/cloudinary.js` wraps the Cloudinary Node SDK (`cloudinary.config()` reads `CLOUDINARY_URL` from the environment automatically) with a small `uploadBuffer()` helper using `upload_stream` — files are held in memory (`multer({ storage: multer.memoryStorage() })` in `backend/src/routes/productFiles.js`) and streamed straight to Cloudinary, **never written to the container's own disk** (irrelevant for correctness locally, but would be silently lost on every Railway redeploy if it ever touched disk there, since that filesystem is ephemeral). `POST /products/:id/files` validates `category` is one of the two allowed values before uploading (fails fast, doesn't waste an upload on a bad request), and `product.files` is now embedded in the product shape everywhere else already returns `workflow`/`comments` (`mapFile`/`mapProduct` in `ordersQueries.js`). **`DELETE /products/:productId/files/:fileId` existe desde 2026-08-03** — ver "Excluir arquivo de produto" abaixo; até lá a tabela era só-adiciona, seguindo o precedente dos comentários. Um arquivo órfão deixado no Cloudinary quando o *produto ou o pedido* é excluído continua sendo lacuna conhecida e aceita (o `ON DELETE CASCADE` limpa a linha do banco, não os bytes lá). Requires a `CLOUDINARY_URL` env var (`.env.example` in both `backend/` and set on Railway) — **non-obvious deploy gotcha hit while building this**: `railway restart` does **not** pick up a variable changed after the last real deploy (it seems to reuse that deployment's captured environment snapshot) — only a fresh `railway up` actually bakes in the current variable values, confirmed by hitting a genuine "Invalid Signature" Cloudinary error that only went away after a real redeploy, not a restart.
- **`NewOrder` creates a real (draft) order on mount**, via `createOrder()` from the context, and keeps its id in local state. Because `<StrictMode>` (in `main.jsx`) intentionally double-invokes effects in development to catch impure side effects, the creation is guarded with a `useRef` flag (`hasCreatedOrder`) so it only actually runs once — without this guard, opening `/pedidos/novo` in dev would silently create two orders. The "Prazo de entrega" input is wired to `updateOrderInfo(orderId, {...})`; client fields are a separate local draft (see `ClientFields`/`clientDraft` above); Vendedor is still unwired (out of scope for this pass).
- **"Finalizar Pedido"** (`handleFinalizeOrder` in `NewOrder`, bottom of the page, `.finalize-order` in `src/styles/forms.css`) validates `clientDraft.personName`/`.document`/`.phone` and at least one product, then resolves/creates the client, attaches `clientId`, calls `finalizeOrder(orderId)`, and navigates to `/pedidos/{orderId}`. Until this is clicked, the order stays a draft (`isDraft: true`) and is invisible on `Orders`/`Production` — this is what stops a half-filled or abandoned Novo Pedido session from cluttering the rest of the app. If the vendedora navigates away without finalizing, the draft order is simply left behind in memory (harmless — it disappears on reload, same as everything else without a backend); nothing currently cleans it up early, and nobody has asked for that.
- **`OrderDetails` reads the real order from the route**, via `useParams()` → `id` → `orders.find(o => o.id === id)`, instead of a hardcoded "PED-2026-0001". If the id doesn't match any order, it renders "Pedido não encontrado." — this can happen since orders created in one session don't persist past a reload.
- **`Orders` (the list) and `Production` (the Kanban) both read from `useOrders()` too** — `Orders` maps `orders` directly; `Production` flattens every order's `products` into one list (tagging each with `orderId`) via `orders.flatMap(...)`, same shape it used to fake locally.
- **Adding a product is a 2-step wizard inside one `Modal`** (`src/components/ui/Modal.jsx`), driven by `useProductList`'s `addStep: 'info' | 'operations'`: step `'info'` collects tipo/modelo/cor/tecido/quantidade/observações; clicking "Próximo" validates (tipo + quantidade required) and advances to step `'operations'`, which shows `OperationsChecklist`; "Voltar" returns to `'info'` without losing what was typed, "Salvar" creates the product with both the info *and* the chosen workflow at once. This is one continuous modal, not two — the wizard step only changes its *content* and title. There is no gate on this: operations are selectable immediately, at creation time (see domain model above).
- **Editing an existing product's workflow later is a separate, second `Modal`** (`isEditModalOpen`/`openEditModal`/`closeEditModal` in the hook), opened via the `ProductCard`'s "Editar" button — same `OperationsChecklist`, but only touches `workflow`, not the other fields. Always available, no gate.
- **`Production` (`/producao`) is a per-operation Kanban board**, not a per-order/per-product view: a `.tabs` row (reusing the pre-existing, previously-unused `.tabs`/`.tabs button` classes from `App.css`) lets you filter to one operation (Corte, Costura, Bordado, ...); within that operation, three columns (`Pendente`/`Em andamento`/`Concluído`, `src/styles/production.css`'s `.kanban-board`/`.kanban-column`/`.kanban-card`) list every product across **all real orders in the shared store** that has that step. This is the only place in the app where `status` actually changes — everywhere else it's just set to `'pending'` on creation.
- **Status moves both forward and backward** (`moveProductStepStatus(orderId, productId, step, 'forward' | 'backward')` in `OrdersProvider`, via `getNextStatus`/`getPreviousStatus`): the Kanban card's own "Voltar"/"Iniciar"/"Concluir" buttons only affect the currently-selected operation. Clicking a product's name opens a detail `Modal` showing **all** of that product's operations at once (not just the selected tab), each independently steppable forward/backward — this is how you reopen an *earlier* operation (e.g. redo Costura after a defect is found during Bordado) without switching tabs. **Completing one operation never auto-affects any other operation's status** — but starting one *can* now be blocked by the sequence-position gate described in the domain model above (added 2026-07-06); once a step has left `'pending'`, nothing about other steps affects it further.
- **A product's design work is tracked by `product.designStatus`** (`NULL` = not in the design queue, else `'pendente' | 'em_design' | 'aprovacao' | 'concluido'` — item 3.1, 2026-07-10, migrations `0002`/`0003`): the columns of the `/design` kanban, in that order (`'aprovacao'` = layout sent to the client; named that in the *product* flow even though an order stage is also called Aprovação — Pablo's requested column name). **Two entry paths, distinguished by `products.design_is_rework`** (`designIsRework` in the API): the *normal flow* (order advances Venda→Design → every product with `design_status IS NULL` auto-enters as `'pendente'`, `is_rework = false` — trigger inside `PATCH /orders/:id/advance-stage`, same transaction; **a product added to an order that has already left `'venda'` is likewise born `'pendente'`**, whatever stage the order is in — `entersDesignQueue` in `backend/src/routes/orderProducts.js`) and *real rework* (the "Retrabalho de design" checkbox in Produção → `'pendente'` with `is_rework = true`, via its own `PATCH /products/:id/design-rework`). **`needsDesignRework` is derived as "active rework"**: in queue (not `'concluido'`) AND `design_is_rework` — so the rework badges (Orders, Produção, and inside `/design` cards) only light up for genuine client-requested rework, never for normal design flow; the checkbox reflects/controls only the rework marker. Unchecking clears the flag; it only removes the product from the queue if still `'pendente'` (in-progress cards stay, just lose the badge) — confirmed with Pablo. **Second trigger, the reverse direction (remapped 2026-07-11 — Pablo's explicit spec after spotting the old mapping was stale)**: design-kanban moves push the order stage along, evaluated as two *state-based* checks (not transition-based) run in sequence after any design-status change (inside `PATCH /products/:id/design-status`, same transaction): (1) order in `'design'` + every product at `'aprovacao'`-or-beyond → stage becomes `'aprovacao'`; (2) order in `'aprovacao'` + every product `'concluido'` → stage becomes `'producao'`. Running both in sequence covers the skip case (everything already `'concluido'` while still in `'design'` advances twice, straight to `'producao'` — only reachable via direct API, the kanban moves one column at a time). A `NULL` `design_status` blocks both checks (product not in the queue = not accounted for). The response carries `orderStage` so the front updates without refetch — same bolt-on pattern as `orderTotalValue`. Rework completion never touches stage (the stage guards hold: a typical rework's order is already `'producao'`); "Reabrir"/backward moves never regress stage (there is simply no UPDATE in that direction). **This means Aprovação→Produção is now automatic too** — `'producao'` is no longer a manually-clicked "client approved" milestone; the manual "Avançar etapa" only remains truly manual for Venda→Design (plus the anti-stuck re-enable described in the tracker rework below). Every transition is logged to `product_events` with `payload.trigger` (`'order-stage'` | `'manual'` | `'rework-checkbox'`), plus `design_rework_flagged`/`_unflagged` events — the seed of item 3.3's history.
  - **The "product added later" entry path was widened from `stage === 'design'` to `stage !== 'venda'` on 2026-07-25, after Pablo hit the gap in real use.** The original test was too narrow *because of the very automation described above*: the design-kanban triggers move the order stage on their own, so by the time someone adds a product the order has often already slid to `'aprovacao'` or `'producao'` — and in those two cases the new product was born with `design_status = NULL`, i.e. **invisible to design, with nothing anywhere to signal it**. Pablo's workaround was to regress the order to Venda and advance it again, which worked only because the Venda→Design trigger sweeps every product still `NULL`. A product added after the sale always needs artwork (the designer has never seen that piece), so the queue entry now applies at every stage past Venda. **Two deliberate non-changes, confirmed with Pablo**: the order stage does *not* regress (other products may genuinely be in production; the system never auto-regresses stage anywhere else either), and the product enters as normal flow, *not* `is_rework` (the rework badge means "client asked to redo existing artwork" — reusing it for a brand-new product would blur two different signals). The freio that keeps this coherent costs no new rule: an order in `'aprovacao'` already only auto-advances to `'producao'` when *every* product is `'concluido'`, so a newly added `'pendente'` product holds the order back by itself. Verified across all four stages plus that freio (10 API checks) and through the browser on Pablo's exact path (7 checks).
- **That same `.rework-badge` also shows on `Orders`**, on any order card where `order.products.some(p => p.needsDesignRework)` — an interim visibility fix (2026-07-03) since there's no design-specific queue/role yet for someone to actually be routed to. This is a stopgap, not the real fix: it just makes the flag visible somewhere a human might glance at it, without any notification or routing. **The design queue this was waiting for now exists** (`/design`, item 3.1 — no per-sector roles yet, so it's just another screen anyone can open, like Produção); the badge on Orders stays as extra visibility, no longer the only surfacing of the flag.
- **Styling**: global styles/resets in `src/styles/variables.css` and `src/styles/global.css`; each feature area (`orders.css`, `dashboard.css`, `sidebar.css`, `forms.css`, `buttons.css`, `layout.css`, `workflow.css`, `products.css`) has its own file, all imported centrally via `index.css`. `App.css` no longer exists — every rule it had was either moved into the matching feature file or dropped if genuinely dead (see "Fechamentos rápidos" item 2.2). New styles go straight into the relevant feature file. Follow the existing plain-class naming style (e.g. `product-card`, `dashboard-card`, `stage completed`).
- **State management**: shared app data (orders + their nested products) lives in `OrdersProvider`'s React Context, wrapping the whole router — this is what lets `NewOrder`, `OrderDetails`, `Orders`, and `Production` all see the same data instead of each having its own copy. Purely UI-local state (which modal is open, a form draft, which tab is selected) is still plain `useState` per component/hook — don't move that into the context, only shared *data* belongs there. **As of the backend migration's step 5 (2026-07-06), this Context is a client-side cache of the real Postgres database, not the source of truth** — `OrdersProvider`/`ClientsProvider`/`OperationsProvider` fetch from the backend API on mount and persist every mutation through it (see "Backend migration roadmap" below), so a page reload now re-fetches the same data instead of resetting to seed data. The frontend and backend are still separate dev processes though — running just `npm run dev` in the repo root is no longer a fully self-contained loop; the backend (and Postgres) must also be running.

## Backend migration roadmap (2026-07-04 → 2026-07-06) — ✅ etapas 1 a 7 concluídas

**Por quê**: o sistema seria usado por várias pessoas em computadores diferentes na Kavi (vendedora criando pedidos, produção acompanhando); estado em memória/Context não sobrevive a outra máquina nem a um reload.

**Stack decidida**: Node + Express (mesma linguagem do front, por continuidade de aprendizado), PostgreSQL, Railway para backend + banco, Vercel para o frontend. O front foi preservado arquiteturalmente — os Providers passaram a buscar/persistir por REST mantendo a mesma forma de dados para páginas/hooks/componentes.

Abaixo o resumo por etapa: **o que foi decidido e as armadilhas que ainda valem hoje**. A narrativa de verificação passo a passo foi removida por já não informar decisão futura.

1. **Schema** (`backend/src/db/schema.sql`, decisões também comentadas lá). `orders` tem `id` numérico como PK **mais** um `order_number` separado (a string "PED-2026-0001") com `UNIQUE` próprio — escolhido em vez de usar a string como PK, por eficiência de join/índice e para desacoplar identidade interna do código de exibição. `stage`/`status` são `TEXT` + `CHECK`, **não `ENUM` nativo** (ENUM é doloroso de estender depois: não existe `ALTER TYPE ... ADD VALUE` transacional simples). **`product_workflow_steps.step_name` é texto livre, sem FK para `operations`** — a "outra operação" digitada à mão não precisa existir no catálogo, e uma FK aqui quebraria esse comportamento já validado.

2. **Setup do backend**. `backend/` é irmão de `src/`, no mesmo repo, ESM de ponta a ponta (`"type": "module"`, igual ao front): `server.js` (entry, lê `PORT`), `app.js` (`cors()`, `express.json()`, `/health` e o error middleware de 4 argumentos no fim), `db/pool.js` (`pg.Pool` lendo `DATABASE_URL`). `cors()` está lá desde o início porque front (5173) e backend (3333) são origens diferentes.
   - **Armadilha preservada como comentário em `pool.js`**: imports ESM são totalmente avaliados **antes** do código top-level do arquivo que importa, então `dotenv.config()` precisa ser chamado **dentro do próprio `pool.js`** — senão `DATABASE_URL` está `undefined` na hora de construir o `Pool`.
   - `/health` não checa só que o Express subiu: roda `SELECT 1` no banco real e devolve `{ status: 'degraded', database: 'unavailable' }` com HTTP 503 se falhar.
   - **O `eslint.config.js` do frontend ignora `backend/`** (a config `globals.browser` não conhece `process` e erraria em todo arquivo). **O backend não tem lint próprio** — para sanidade, `node --check` nos arquivos tocados.
   - `backend/.env` é gitignorado; só o `.env.example` é commitado.

3. **API de pedidos/produtos**. Três arquivos de rota: `routes/orders.js` (list/get/create/patch/finalize/advance-stage), `routes/orderProducts.js` (`POST /orders/:orderId/products`, montado à parte com `Router({ mergeParams: true })` para não ficar também acessível em `/products` puro) e `routes/products.js` (patch/delete/`PUT .../workflow`/`PATCH .../workflow/:step`).
   - `db/ordersQueries.js` concentra o compartilhado: `mapOrder`/`mapProduct` traduzem o snake_case do banco (`client_id`, `needs_design_rework`) para o camelCase que o front já usava; **`fetchOrders` faz 3 queries simples** (pedidos, produtos deles, etapas desses produtos) e agrupa **em JS** no formato aninhado `order.products[].workflow[]`, em vez de `json_agg` no SQL.
   - **`ORDER_STAGES`/`getNextStatus`/`getPreviousStatus` são DUPLICADOS de `src/data/orderStages.js` e do `OrdersProvider`, não importados** — são processos Node separados. **Se a ordem dos estágios ou as transições de status mudarem, sincronize os dois lados à mão.**
   - `db/withTransaction.js` envolve um client em `BEGIN`/`COMMIT`/`ROLLBACK` para o que precisa suceder ou falhar junto: criar pedido (insert com `order_number` placeholder e depois `UPDATE` para `PED-{ano}-{id}` quando o id real volta do `RETURNING`), criar produto com as operações escolhidas (todas como `'pending'` — escolher é venda, o status é que é produção) e o diff do `PUT /products/:id/workflow` (etapas que continuam selecionadas **mantêm o status**, novas entram `pending`, desmarcadas são apagadas — é o equivalente servidor do `saveWorkflow`, preservando progresso em vez de zerar).
   - `utils/asyncHandler.js` existe porque o **Express 4 não captura promise rejeitada** dentro de handler `async`; toda rota é embrulhada nele.

4. **API de clientes/operações/comentários**. `routes/clients.js`, `routes/operations.js`, `routes/productComments.js` (montado como o `orderProducts.js`).
   - **`POST /clients/find-or-create` casa só por `document`** (nunca telefone — mesmo raciocínio do domain model) e trata a corrida rara de dois requests que erram o lookup e ambos tentam inserir: o perdedor pega o `23505` (unique violation) do Postgres e apenas re-busca, em vez de errar. `POST /clients` e `POST /operations` transformam o mesmo `23505` em **409** com mensagem em linguagem simples.
   - **`DELETE /operations/:id` deleta por id numérico, não por nome** — nomes como "Revisão/Finalização" contêm `/`, que o Express quebraria em segmentos de caminho. É por isso que `GET /operations` devolve `[{ id, name }]` e não `string[]`.
   - Comentários passaram a vir **embutidos no produto** em toda resposta que devolve produto (`mapProduct` ganhou `commentRows`), mais antigos primeiro — "mais novo primeiro" continua sendo preocupação só de exibição do `ProductCard` (`.slice().reverse()`).
   - **Não construído**: `PATCH`/`DELETE` de clientes, e editar o nome de uma operação (só adicionar/remover).

5. **Front conectado à API**. Os três Providers deixaram de semear de `src/data/*.js` e passaram a buscar na montagem e persistir cada mutação. `src/services/api.js` é um cliente fetch fino: um `request()` (base em `VITE_API_URL`, default `http://localhost:3333`; lança um `Error` amigável de "servidor não respondeu" se o próprio fetch falhar) mais `ordersApi`/`productsApi`/`commentsApi`/`clientsApi`/`operationsApi` espelhando as rotas um a um.
   - **Contrato único dos mutators, seguido até hoje**: todos são `async`; no sucesso devolvem o recurso criado/atualizado (ou só o id, em `createOrder`/`findOrCreateClient`); na falha **eles mesmos dão `alert()` com a mensagem do servidor e devolvem `null`**. As páginas não precisam de `try/catch` — fazem `const r = await mutator(...); if (!r) return;` antes de fechar modal, navegar ou limpar draft.
   - **`OperationsProvider` guarda `{id, name}` internamente mas expõe `operations` como `string[]`** (via `.map`), por isso `Settings`, `Production` e `OperationsChecklist` não precisaram mudar; `removeOperation(name)` resolve o id por dentro.
   - **Ids inventados no cliente sumiram**: `id: Date.now()`, o array de workflow montado à mão e o `createdAt` pré-formatado viraram responsabilidade do servidor.
   - **Duas surpresas de forma, corrigidas aqui e ainda válidas**: (1) `orders.id` (PK numérica) e `orders.order_number` são colunas diferentes, mas todas as telas exibiam `order.id` achando que era o código legível — **todo lugar que EXIBE usa `order.orderNumber`, enquanto rotas, keys e chamadas de API usam `order.id`**; (2) colunas `DATE` voltam do `pg` como objeto `Date` e serializam como ISO completo (`"2026-08-01T03:00:00.000Z"`), quebrando em silêncio o `<input type="date">` — corrigido **na origem**, com `pg.types.setTypeParser(1082, v => v)` em `pool.js` (OID 1082 = `date`), para `DATE` trafegar como texto puro.
   - **`Production` deriva a aba ativa no render** (`manuallySelectedOperation ?? operations[0]`) em vez de sincronizar por efeito: `operations` começa vazio até a API responder, então um valor inicial ficaria preso em `undefined` para sempre. É também o único formato que o `react-hooks/set-state-in-effect` aceita sem aviso.
   - **Consequência prática**: `npm run dev` sozinho na raiz **deixou de ser um ciclo de desenvolvimento completo** — backend e Postgres precisam estar de pé.

6. **Deploy: Railway (backend + Postgres) + Vercel (frontend)** — split deliberado, decidido com o Pablo, em vez de tudo numa plataforma só.
   - **Railway** (projeto `texflow`): dois serviços, o plugin gerenciado de **Postgres** e o **backend**, publicado com **`railway up backend --path-as-root --service backend`** (sobe só a pasta `backend/` como contexto de build — escolhido em vez de conectar ao GitHub, que exigiria configuração extra de root directory neste monorepo). **Não há auto-deploy por git: `git push` NÃO redeploya o backend.** O `DATABASE_URL` do serviço é `${{Postgres.DATABASE_URL}}` (referência entre serviços, sobrevive a rotação de credencial) e resolve para o endereço **interno** `postgres.railway.internal`; o `DATABASE_PUBLIC_URL` (`*.proxy.rlwy.net`) existe só para acesso local pontual (`psql`, `npm run migrate`, `createUser.js`). Domínio: `https://backend-production-e28f.up.railway.app`. `PORT` é injetado pela plataforma e o `server.js` já o lia.
   - **Vercel** (projeto `tex-flow/texflow`, `https://texflow-blue.vercel.app`), publicado da raiz. **`vercel.json` na raiz é obrigatório, não opcional**, por dois motivos: (1) o rewrite `/(.*)` → `/index.html`, sem o qual dar F5 em qualquer rota do react-router (`/pedidos/3`) devolve 404; (2) `"framework": "vite"` — a detecção automática de monorepo viu o `backend/` e fixou o preset do **projeto** em "Services" **no servidor**, e nenhuma edição local do arquivo desfazia isso; declarar o framework no `vercel.json` é o que sobrepõe por deploy. `VITE_API_URL` é variável **de build** (o Vite injeta na compilação, não lê em runtime), então mora nas settings da Vercel. O `cors()` permissivo do backend dispensou mudança para o browser chamá-lo do domínio da Vercel.
   - **A Vercel É git-connected**: push na `main` redeploya o frontend sozinho. **Essa assimetria com a Railway é a origem de vários incidentes registrados adiante** — ver a regra consolidada no fim do roadmap de produção.
   - **Não feito**: domínio próprio; observabilidade/error tracking em qualquer das duas.

7. **Autenticação** (login básico; papéis por setor só vieram em 2026-07-29). Escopo reduzido de propósito, confirmado com o Pablo: um único `role: 'admin'` com acesso a tudo — o objetivo era só parar de ficar totalmente aberto.
   - **Schema**: tabela `users` com `username` único, `password_hash` (bcrypt, nunca texto puro) e `role TEXT CHECK (...)` — o CHECK de valor único era intencional, e relaxá-lo depois não exigiu ferramenta nenhuma, só a migration `0005`.
   - **JWT, não sessão por cookie** — escolhido justamente porque front (Vercel) e backend (Railway) estão em origens diferentes: um `Authorization: Bearer` não tem complicação de `SameSite`/cookie cross-site e é stateless (verifica assinatura contra `JWT_SECRET`, sem tabela de sessões). `POST /auth/login` confere com `bcrypt.compare` e assina 7 dias com `{ id, username, role }`.
   - **`middleware/requireAuth.js`** é montado **depois** de `/auth` (para o próprio login e o `/health` ficarem públicos) e **antes** de todos os outros routers: 401 sem token/inválido/expirado, senão popula `req.user` e segue. Nenhuma rota mudou lógica por causa dele.
   - **Não existe endpoint público de registro, de propósito** — criar conta nunca é exposto por HTTP. É o script manual `backend/src/scripts/createUser.js <username> <senha> [papel]`, rodado localmente e, contra produção, com `DATABASE_URL="$DATABASE_PUBLIC_URL"`.
   - **Front**: `AuthProvider`/`useAuth()` no mesmo padrão de dois arquivos dos outros contexts, com token/usuário em `localStorage` (sobrevive a reload); `Login` virou formulário real; `ProtectedRoute` envolve tudo menos `/login`. O `request()` anexa o `Authorization` lendo **direto do `localStorage`** (é módulo puro, não passa por context) e **se auto-desloga em qualquer `401` fora do `/auth/login`**.
     - ⚠️ **É por causa desse auto-logout que erro de permissão precisa ser 403, nunca 401** — ver o item 1.3 dos fechamentos rápidos (onde isso foi um bug real) e o `requireRole` em "Papéis por setor".
   - **Correção não óbvia nos Providers**: os três buscam na montagem e ficam **acima** do `<BrowserRouter>`, então o `ProtectedRoute` não impede que montem — bateriam na API já protegida ainda na tela de login, alertando um 401 cru antes de a pessoa digitar a senha. Cada efeito de fetch passou a ser gateado por `useAuth().isAuthenticated`, re-rodando sozinho quando vira `true`. **Armadilha de lint**: a primeira versão também zerava o estado no ramo "não autenticado", o que o `react-hooks/set-state-in-effect` proíbe; foi **removido em vez de contornado**, já que o `ProtectedRoute` esconde tudo antes de dado velho aparecer.
   - **Limitação estrutural que vale para tudo que viaja no token**: desativar alguém (`is_active`) ou trocar o papel de alguém **só vale no próximo login dessa pessoa** — não há revogação, e isso é consequência consciente da escolha stateless.
   - **Deploy desta etapa deixou a lição registrada**: o push subiu o frontend na Vercel automaticamente, mas o backend, a tabela `users` e a primeira conta admin tiveram que ir à mão para a Railway. **Nunca presuma que um `git push` sozinho publica uma mudança que toca o backend.**

## Fechamentos rápidos (roadmap 2026-07-10) — ✅ as três fases fechadas

Punch list escrita pelo próprio Pablo, em três fases: fechamentos rápidos de baixo risco, dívida técnica de infra, e features novas. Mesma regra de um item por vez.

**Fase 1**

1. **Autor do comentário auto-preenchido** — `useProductList` passou a chamar `useAuth()` internamente (hook compondo hook, que é o ponto de hooks) e semeia `commentDraft.author` com o `username` em `openCommentsModal`. O `<Input>` "Autor" saiu dos **dois** lugares que renderizam o modal (`OrderDetails` e `NewOrder` — esse JSX é duplicado entre as duas páginas desde que comentários existem), e a validação de "autor preenchido" caiu junto. **`product_comments.author` continua `TEXT`, não FK para `users.id`** — mudou só o que preenche o texto; um `author_id` de verdade é mudança bem maior e separada.

2. **CRUD completo de `users`** — até aqui só existia o `createUser.js` (create-only). `routes/users.js` (atrás do `requireAuth` como tudo): `GET /`, `GET /:id`, `PATCH /:id` (**só `username`** — troca de senha é o item 3, porque exige conferir a senha atual e merece rota própria) e `DELETE /:id`.
   - **`DELETE /:id` é soft delete, nunca `DELETE FROM`** — coluna `users.is_active`; a rota a põe em `false`. Duas travas antes: **não pode desativar a própria conta** (impede um admin de se trancar para fora por acidente) e **não pode desativar o último usuário ativo do sistema** (defesa em profundidade — a primeira trava já cobre o caso comum; esta só importa para um usuário já desativado, com JWT ainda válido, tentando derrubar a única conta legítima).
   - **`POST /auth/login` passou a checar `is_active`**, dobrado **dentro do mesmo ramo e mensagem genérica** de "Usuário ou senha inválidos" que já servia a usuário inexistente e senha errada — preserva a intenção anti-enumeração, em vez de acrescentar um "conta desativada" que revelaria qual dos três falhou.
   - **Desativar não revoga token já emitido** (JWT stateless, sem tabela de sessões): o token vale o resto dos 7 dias, só logins novos são bloqueados. Documentado no `schema.sql` e aceito — revogação de verdade contradiria a decisão original e ninguém pediu.

3. **Fluxo de troca/reset de senha** — `PATCH /users/:id/password`, deliberadamente separado do PATCH genérico porque a regra **muda conforme o alvo**:
   - **A si mesmo**: `currentPassword` obrigatório, conferido com `bcrypt.compare` antes de aceitar o novo.
   - **A outra conta** (admin resetando): não exige senha atual, reset direto, **sem fluxo de e-mail/token** — é ferramenta interna. `newPassword` mínimo de 6 caracteres, checado no servidor (o `createUser.js` segue como script manual confiável, sem essa validação).
   - ⚠️ **Senha atual errada devolve 403, NÃO 401 — e isso foi bug real pego em teste manual, não desenho prévio.** O `request()` do front trata **qualquer** 401 fora do `/auth/login` como sessão expirada e **desloga à força**; com 401, um simples erro de digitação expulsava a pessoa em vez de mostrar o erro. 403 ("autenticado, mas esta ação é negada") escapa do handler global. **É essa a razão de o `requireRole` também responder 403** (ver "Papéis por setor").
   - **Sem tela nova**: virou uma seção **"Usuários" dentro de `Configurações`**, por ser a mesma natureza de configuração administrativa que a lista de operações e o template do WhatsApp já ocupavam — uma página/rota inteira só para isso seria desproporcional. Busca a lista com `useState`/`useEffect` local, **sem context compartilhado** (mesma decisão de `Reports` — nenhuma outra tela consome). Tem "Minha Senha" (atual/nova/confirmar) e, por usuário, "Redefinir Senha" e "Desativar". **Não existe "Reativar"** (não há rota; o `PATCH` só aceita `username`) — não foi pedido, e dá para consertar no banco se um dia precisar.

**Fase 2 (dívida técnica de infra)**

2.1. **Migration runner + seed** — `backend/src/db/schema.sql` virou a migration `0000_schema.sql` (todos os `CREATE TABLE` como `IF NOT EXISTS`): sempre roda primeiro, segura tanto em banco novo quanto em já provisionado, e por isso deixou de ser um arquivo especial "aplicar à mão uma vez". **De agora em diante, mudança de schema é arquivo numerado em `backend/src/db/migrations/`, nunca edição do `schema.sql`.** `npm run migrate` cria `schema_migrations(filename, applied_at)` e roda o baseline + o que ainda não foi aplicado, **cada arquivo na própria transação**, registrando o nome logo depois para nunca repetir. `npm run seed` é passo separado e opcional: as 8 operações padrão com as posições de sequência documentadas no domain model (`ON CONFLICT (name) DO NOTHING`) mais um cliente/pedido/produto de demonstração, guardado por um `document` fixo reconhecível (`'00000000000'`) — re-executável sem duplicar.

3.3. **Histórico completo por pedido/produto** — fecha a Fase 3. Quatro decisões tomadas com o Pablo antes de codar:

É o `order_id` que faz a timeline do pedido ser **uma query** (`WHERE order_id = X`), já trazendo junto tudo que aconteceu com os produtos dele — em vez de uma tabela `order_events` paralela e um merge de dois formatos. **O nome da tabela continua `product_events`** (renomear obrigaria a mexer no `schema.sql`, na migration `0002` e em todos os pontos de leitura/escrita, sem ganho funcional) — mas o escopo dela hoje é maior que o nome sugere.

Se `orderId` não vier mas `productId` sim, um `COALESCE` com subquery deriva o pedido a partir do produto, para a timeline nunca perder um evento por esquecimento de quem chamou. `fetchOrderEvents` faz `LEFT JOIN` (não `INNER` — evento de pedido não tem produto) e devolve um `productLabel` pronto.

É duplicação de dado, **aceita porque `PATCH /products/:id/workflow/:step` é o único lugar do sistema que muda status de etapa** — as duas não têm como divergir sem alguém mexer justamente ali.
   - **Eventos registrados**: `order_created`, `order_updated`, `order_finalized`, `payment_registered`, `order_stage_changed`, `product_created`, `product_updated`, `product_removed`, `product_operations_changed`, `workflow_step_changed`, `design_status_changed`, `design_rework_flagged`/`_unflagged`, `comment_added`, `file_uploaded` — mais `file_deleted`, acrescentado em 2026-08-03. ## Papéis por setor (✅ construído, 2026-07-29)

Fecha o maior buraco arquitetural que restava: até aqui existia login (Etapa 7), mas com **um único `role: 'admin'`** que fazia tudo. Quatro decisões do Pablo antes de codar, mais duas colocações dele que mudaram o desenho original:

- **Quatro papéis**: `admin`, `vendedora`, `design`, `producao` (migration `0005`, que troca o `CHECK` antigo de valor único — `CREATE TABLE IF NOT EXISTS` não altera tabela existente, então o baseline `0000` sozinho não bastaria num banco já provisionado). Todo usuário que já existia continua `admin`, sem migração de dado. **São cinco desde 2026-08-03** — `gerente` entrou pela migration `0012`, na mesma forma; ver "Papel `gerente`" abaixo.
- **Matriz "leitura ampla, escrita por setor"**: todo mundo enxerga pedidos, detalhes, histórico, comentários, arquivos, o kanban de design e o de produção; **só quem é do setor consegue mudar**. Confecção pequena — esconder informação criaria mais atrito que risco.
- **`design` acumula `vendedora`** (pedido explícito do Pablo): tudo que a vendedora faz (criar/editar pedido, pagamento, clientes, relatórios) mais mover card no kanban de design. **Consequência registrada na hora**: `design` fica a um passo de `admin` (só não tem Configurações nem mover etapa de produção), e `vendedora` só se distingue de `design` por não mover card.
- **Permissões fixas no código, sem tela de administração de permissões** — decisão explícita do Pablo contra over-engineering. Ajustar quem pode o quê é edição pontual em `backend/src/auth/permissions.js` + a cópia em `src/data/permissions.js`.
- **Sem permissão = some do menu e da tela** (não "aparece desabilitado"). Quem chega por URL direta cai numa tela `.no-access` dentro do `Layout`, em vez de ser redirecionado em silêncio.

**Dentro de `producao`, cada pessoa opera só as etapas atribuídas a ela** (ex.: só Corte e Costura) — não é um papel por etapa. Tabela de vínculo `user_operations (user_id, operation_id)`, apontando para o **mesmo catálogo `operations`** que Configurações já gerencia; não existe lista paralela de etapas. Os dois `ON DELETE CASCADE` limpam sozinhos (remover "Silk" em Configurações apaga os vínculos; apagar um usuário leva os dele — verificado). Três regras:
- **Lista vazia nega tudo**, não libera tudo: esquecer de atribuir gera alguém que não move nada e reclama na hora, em vez de acesso total silencioso.
- **Etapa fora do catálogo** (a "outra operação" digitada à mão na venda) é **livre para qualquer usuário de produção** — mesmo precedente que o gate de sequência já segue (etapa custom não é bloqueada e não bloqueia ninguém).
- **`admin` passa por tudo** — e `gerente` também, desde 2026-08-03 (`ALL_STEPS_ROLES`).

**Não há duplicação com o gate de sequência, e é importante entender por quê**: os dois moram no mesmo `PATCH /products/:id/workflow/:step` (o único lugar do sistema que muda status de etapa), mas respondem a perguntas diferentes — `findBlockingSteps` pergunta *"essa etapa já pode começar?"* olhando o **produto**; `canOperateStep` (`backend/src/db/usersQueries.js`) pergunta *"essa pessoa pode mexer nessa etapa?"* olhando o **usuário**. Verificado que convivem: com Costura atribuída mas Corte pendente, a resposta é `409` (sequência), não `403`.

Detalhes de implementação que não se deduzem do código:
- **`requireRole(...)`** (`backend/src/middleware/requireRole.js`) responde **403, nunca 401** — um 401 fora de `/auth/login` faz o `request()` do front tratar como sessão expirada e deslogar na hora (a mesma armadilha já documentada no item 1.3 dos fechamentos rápidos). A sessão aqui está válida; o que falta é permissão.
- **`GET /clients` ficou aberto a todos os papéis de propósito**, mesmo com a tela `/clientes` sendo restrita: o `ClientsProvider` busca na montagem para *todo* mundo, e `Orders`/`OrderDetails` mostram o nome do cliente. Gatear o GET faria um usuário de produção tomar erro no login. O que é restrito são `POST`/`PATCH`/`find-or-create` e a tela. Mesma lógica para `GET /operations` e `GET /settings/whatsapp-template`.
- **`Configurações` é gateada por seção, não pela rota** — "Minha Senha" mora lá, então fechar a tela inteira tiraria de todo mundo o jeito de trocar a própria senha. As outras três seções (Operações, Mensagem do WhatsApp, Usuários) só aparecem para admin, e o `GET /users` só é chamado se for admin (senão a tela alertaria um 403 na cara de quem só queria trocar a senha).
- **O papel viaja dentro do JWT** (stateless, sem tabela de sessões), então **trocar o papel de alguém só vale no próximo login dessa pessoa** — mesma limitação já registrada para `is_active`. A **lista de etapas**, ao contrário, é consultada no banco a cada requisição, então vale na hora (no front, depois de um reload: o `AuthProvider` busca `GET /users/:id/operations` na montagem).
- **Não pode trocar o próprio papel** (400) — um admin se rebaixando perderia a tela na hora, sem ninguém para desfazer. Espelha a trava de não desativar a si mesmo que já existia.
- **Marcar "Retrabalho de design" é `SALES_ROLES`, não `DESIGN_ROLES`**, mesmo o checkbox morando na tela de Produção: originar uma demanda de design vem de quem fala com o cliente ou do próprio designer, não da produção.
- **Escolher *quais* operações o produto precisa (`PUT /products/:id/workflow`) é `SALES_ROLES`** — decisão de venda, conforme o domain model; mover o *status* de uma etapa é que é da produção.
- **Frontend**: `src/data/permissions.js` é a cópia da matriz (só esconde; quem barra é o servidor), `useAuth()` passou a expor `can(action)` / `canOperateStep(step, catalog)`, `ProtectedRoute` ganhou a prop `action`, o `Sidebar` filtra `NAV_ITEMS` por `action` e mostra o papel abaixo do nome (sem isso, "sumiu o menu Clientes" vira mistério). O `ProductCard` lê a permissão do contexto em vez de receber por prop — ele é usado em três telas e as três teriam que repassar a mesma coisa.
- **No kanban de design, o gate envolve o bloco inteiro de ações**, não cada um dos quatro botões: foi exatamente esse tipo de condição repetida que sumiu com todos os botões da tela em 2026-07-25.
- `createUser.js` aceita o papel como terceiro argumento (`node src/scripts/createUser.js <username> <senha> [papel]`), com `admin` como padrão para o comando de sempre continuar funcionando.

**Verificado** por API e navegador com um usuário descartável por papel: leitura liberada a todos; escrita de pedido/cliente/relatório negada à produção; Configurações e `/users` só admin; senha própria vs. de terceiros; papel inválido e troca do próprio papel; o gate por etapa em todas as combinações, incluindo etapa custom liberada e o `409` de sequência convivendo com o `403` de permissão; cascata ao remover operação; e nas telas, menu filtrado, botões ausentes/presentes, tela "Sem acesso" por URL direta, atribuição de etapas persistindo no servidor e o fluxo real de produção (Corte iniciar→concluir→Costura liberar) feito pelo usuário de produção.

### Item 3 — Grade de tamanhos (migration `0006`)

Decisões do Pablo:
- **Lista fixa de 19 tamanhos**, não texto livre: `1, 2, 4, 6, 8, 10, 12, 14, 16, PP, P, M, G, GG, EXG, G1, G2, G3, G4`. O conjunto da Kavi é fechado e conhecido, diferente de Modelo/Cor/Tecido — evita erro de digitação e acelera o preenchimento. Tamanho novo no futuro = mudança pontual, sem tela de catálogo.
- **`products.quantity` vira a SOMA da grade**, calculada no servidor, com o campo virando somente-leitura na tela. **O motivo é dinheiro**: o valor do pedido é `unit_price * quantity`, e grade somando 10 com quantidade dizendo 12 deixaria ninguém sabendo qual número acreditar. **Produto sem grade continua com a quantidade digitada à mão** — é o caso de todos os produtos que já existiam.
- **`TEXT` + `CHECK`, não `ENUM`** (mesma razão do topo do `schema.sql`), e **a ordem de exibição mora no código**, não no banco: um CHECK valida mas não ordena, e ordem alfabética colocaria `'10'` antes de `'2'` e `'EXG'` antes de `'G'`.

**A grade circula como objeto (`{ P: 2, EXG: 8 }`) dentro do formulário e como lista (`[{ size, quantity }]`) na API** — `sizesToList`/`sizesToMap` (`src/data/sizes.js`) são a fronteira entre os dois formatos, chamadas no `useProductList`. O objeto é o que um campo-por-tamanho preenche naturalmente; a lista é o que a tabela guarda. O `PATCH` aceita editar **só** a grade (daí o `SELECT` de existência: sem UPDATE não haveria como detectar 404), tamanho fora da lista ou repetido é 400, tamanho com 0 é descartado em vez de virar linha, e grade vazia devolve o controle para a quantidade manual.

**Dois achados durante a verificação:**
- **Regressão própria, corrigida**: o histórico mostrava o campo cru `sizes` ("dados alterados (…, sizes)") porque `FIELD_LABELS` (`src/utils/events.js`) não conhecia o campo novo. **Lembrete permanente**: acrescentar campo ao payload de `product_updated`/`order_updated` exige acrescentar o rótulo lá também, senão vaza nome técnico para a tela.
- **Não é regressão** (medido com `git stash` nos dois estados): o checkbox "Vetorizar logo" aparecia esticado porque `.form-grid input { width: 100% }` atinge também `input[type="checkbox"]` — já era assim antes. Corrigido depois, na passada de polish.
- **A execução interrompida em 2026-07-29 era defeito do teste**: ele recarregava `/pedidos/novo`, página que cria um rascunho novo a cada montagem, então o produto anterior não estaria lá mesmo. Reescrito para recarregar o pedido finalizado — ver lição 1 em "Lições de método".

### Item 5 — Design clicável + layout aprovado

- **O card do kanban deixou de ser só o nome**: cor, tecido, quantidade, grade de tamanhos e um selo verde **"Layout aprovado"** quando o arquivo já está anexado — o que bordado, silk e costura procuram antes de começar.
- **Decisão mantida: uma visão única com tudo, não uma variação por etapa.** Corte, Bordado/Silk/DTF e Costura pediam praticamente o mesmo conjunto; uma visão só é menos código e ninguém fica sem informação por um palpite errado de quem precisa dela.
- O modal manteve o que já tinha (etapas independentes com Voltar/Avançar respeitando a permissão por etapa, e o checkbox de retrabalho só para quem pode); o painel entrou acima, separado por uma divisória.

**Bug real encontrado na verificação e corrigido aqui** (não foi introduzido por este item, só ficou evidente nele): `fetchOrders` e `getProductById` buscavam `product_workflow_steps` **sem `ORDER BY`**, então o Postgres devolvia na ordem física das linhas — **que muda quando uma linha é atualizada**. Na prática, a etapa que a pessoa acabava de mover pulava para o fim da lista, embaralhando os chips do `ProductCard` e a lista do modal a cada clique. Comprovado medindo a resposta antes e depois de um `PATCH` (`['Corte','Costura','Silk']` virava `['Costura','Silk','Corte']`). As duas queries agora ordenam por `op.sequence_position NULLS LAST, pws.id` — a **sequência real de produção**, com etapa fora do catálogo indo para o fim e o id desempatando para a ordem nunca variar.

### Item 2 — Aba Conferência (migrations `0007` e `0008`)

Abordagem definida pelo Pablo (segunda versão dele, melhor que a minha proposta): **`Lavagem`, `Revisão/Finalização` e `Embalagem` saem do kanban de Produção** e passam a existir só numa aba nova, **Conferência**, operada pela vendedora. A Produção fica só com a fabricação. Isso **dispensa uma coluna `review_status`**: a Conferência é uma view filtrada sobre o `product_workflow_steps` que já existe.

**Parte 1 — o modelo (`0007`)**:
- **Duas colunas em `operations`, nenhuma tabela nova**: `phase` (`'producao'` | `'conferencia'`) e `auto_add`. Delas saem, da mesma fonte, quais abas cada tela mostra e quem tem permissão de mexer.
- **`auto_add` é coluna, não dois nomes fixos no código**: Revisão/Finalização e Embalagem entram sozinhas em todo produto novo; **Lavagem não** (nem toda peça é lavada, e obrigá-la viraria clique de mentirinha). Hardcodar os dois nomes contrariaria o catálogo ser configurável por princípio, e quebraria se alguém renomeasse a operação em Configurações.
- **A permissão saiu do `requireRole` da rota e foi para dentro do handler**, porque depende de QUAL etapa está sendo movida: fase `'conferencia'` → `SALES_ROLES`; fase `'producao'` → `PRODUCTION_ROLES` **mais** o `canOperateStep`. Etapa fora do catálogo não tem fase e cai em `'producao'`. **A partir de 2026-08-03 a fase `'producao'` tem um terceiro caminho**: quem NÃO é da produção ainda passa se aquela etapa estiver atribuída nominalmente a essa pessoa (`hasStepAssigned`) — ver "Etapa de produção operada por quem não é da produção". **A `phase` não virou, e não deve virar, o interruptor de permissão para esse caso**: ela decide *em qual tela* a etapa aparece, e é exclusiva (ou de um grupo, ou do outro).
- **Reposicionamento obrigatório**: as posições eram Revisão=3, Lavagem=4, Embalagem=5 — o gate de sequência exigia **Revisão antes de Lavagem**, o inverso da sequência combinada. Agora Lavagem=3, Revisão=4, Embalagem=5.
- **Armadilha real evitada**: `PUT /products/:id/workflow` substitui o conjunto de etapas, e o checklist não exibe as automáticas — sem reaplicá-las no servidor, **salvar uma edição de etapas apagaria Revisão/Finalização e Embalagem do produto**. O `PUT` faz a união com as `auto_add`. Pela mesma razão, o `extraSteps` do `OperationsChecklist` (que existe para manter visível uma etapa fora do catálogo) precisou excluí-las, senão voltariam à tela justamente ao editar um produto que já as tem.
- **Entrada automática, com uma exceção**: produto **novo** nasce com Revisão/Finalização e Embalagem; Lavagem continua opcional, escolhida no cadastro. **Produtos que já existiam não receberam retroativamente** — e como a condição de avanço é "todas as etapas de Conferência concluídas", quem não tem nenhuma passa direto e os pedidos em voo não travam.

**Parte 2 — a tela e o aviso (`0008`)**:
- **Novo estágio `'conferencia'`** entre `'producao'` e a entrega. O pedido entra nele **sozinho**, por gatilho em `PATCH /products/:id/workflow/:step` quando toda a fabricação de todos os produtos termina — mesma forma dos gatilhos do design (checagem de estado, na mesma transação, sem caminho de volta). **Só olha etapas de fase `'producao'`**, senão as próprias etapas de Conferência segurariam a entrada na Conferência.
- **`/conferencia` repete de propósito a forma da tela de Produção** (abas por etapa × três colunas de status): é o mesmo gesto, sobre a mesma tabela, só filtrado por `phase` — quem sabe usar Produção sabe usar isto. Clicar no produto abre o mesmo `ProductDetailPanel`.
- **"Pronto" é derivado, não é estágio**: a seção "Prontos para retirada" lista os pedidos cujos produtos concluíram **todas** as suas etapas de conferência, com o botão "Avisar cliente". **O gatilho é do pedido, não do produto** — senão um pedido com 3 produtos mandaria 3 avisos ao cliente.
- **Segunda mensagem de WhatsApp**: chave `whatsapp_ready_template` na tabela `settings` (chave-valor justamente para isto — nenhuma migration), com rota própria, editor em Configurações e os mesmos placeholders. Continua sendo link `wa.me`: **o envio é um clique humano**.
- **Backfill (pedido pelo Pablo)**: os produtos que já existiam nasceram antes da entrada automática e passariam pela Conferência sem ninguém conferir. A `0008` insere Revisão/Finalização e Embalagem como `'pending'` em todo produto de pedido **não-rascunho** (`ON CONFLICT DO NOTHING` protege quem já tinha). **Rascunhos ficam de fora porque podem ser abandonados.**
- **Bug real encontrado na verificação**: `GET /operations` ordenava por `id`, e as abas das duas telas saem dali — na Conferência isso apareceu na cara, com **Revisão/Finalização antes de Lavagem** (Revisão tem id menor por ter sido semeada antes, mas posição 4 contra 3). Agora ordena por `sequence_position NULLS LAST, id`.

### Item 1 — Fechamento do pedido (migration `0009`)

Fecha o ciclo: até aqui não havia como dizer "o cliente buscou, acabou" — o pedido ficava em Conferência para sempre.

- **Sexto e último estágio `'entregue'`** e **`orders.picked_up_at`** — decisão do Pablo: estágio **e** carimbo, não um ou outro; o estágio diz *que* retirou, a coluna diz *quando*, que é o dado de um relatório futuro de prazo real venda→entrega.
- **Sem rota nova**: o `PATCH /orders/:id/advance-stage` ganhou duas particularidades quando o próximo estágio é `'entregue'` — grava `picked_up_at = now()` no mesmo `UPDATE`, e **é o único avanço com trava de verdade no servidor** (409 se algum produto ainda tem etapa de Conferência pendente, listando quais). Isso é diferente do "Avançar etapa" desabilitado em Design/Aprovação, que é só dica visual: **dizer que entregou sem ter conferido é um erro de registro que ninguém desfaz depois**.
- **A regressão limpa o carimbo**: sair de `'entregue'` volta `picked_up_at` para NULL — regressão existe para corrigir clique errado, e **data de retirada num pedido não retirado é pior que data nenhuma**.
- **Na tela**: em Conferência o botão "Avançar etapa" **passa a se chamar "Registrar retirada"** (mesma transição, mas quem clica está afirmando que o cliente levou a peça), desabilitado enquanto a conferência não termina, com `.stage-hint` explicando. `OrderDetails` mostra "Retirado em" quando existe.
- **Pedido entregue sai das telas de trabalho** (`Production`, `Conference`) e deixa de contar como "ativo" no Dashboard — senão o número só cresceria para sempre. Continua na lista de Pedidos, que é o histórico.

### Item 6 — Esqueci minha senha (migration `0010`) — fecha o roadmap

Os usuários da Kavi não têm e-mail cadastrado, então não existe reset por link: a pessoa registra um pedido pela tela de login e um admin aprova dentro do próprio sistema.

- **`POST /auth/password-reset-request` é a única rota pública além do login e do `/health`** — e tem que ser: quem esqueceu a senha não consegue se autenticar para pedir. Fica em `auth.js` porque é o único router montado **antes** do `requireAuth`.
- **Anti-enumeração**: responde sempre a mesma mensagem de sucesso, exista o usuário ou não — mesma convenção do login.
- **Índice UNIQUE parcial** (`WHERE status = 'pendente'`): no máximo um pedido pendente por usuário, quantos resolvidos quiserem. Sem ele, cinco cliques em "esqueci minha senha" virariam cinco linhas na fila do admin — e a rota é pública, então nem precisa de má intenção.
- **Ordem das rotas importou**: `/users/password-reset-requests` precisa ser declarada **antes** de `/users/:id`, senão o Express lê o caminho como um id. Mesma armadilha já registrada no `App.jsx` (`/pedidos/novo` antes de `/pedidos/:id`).
- **Aprovar devolve a senha para `kavi2026`** (decisão do Pablo, mantida depois de eu levantar que isso deixa a conta com senha conhecida até a troca; o raciocínio dele é que a pessoa troca no primeiro acesso). A troca de senha e o fechamento do pedido acontecem **na mesma transação**. A resposta devolve a senha padrão para a tela mostrá-la a quem aprovou — é o admin que avisa a pessoa. **O sistema NÃO obriga a troca no primeiro acesso**; não existe esse mecanismo.
- **Sem notificação ativa**: a seção "Pedidos de senha" em Configurações só aparece quando há pendentes. Não há e-mail, badge no menu nem push — combinado que o canal é "dentro do sistema".

## Pedido entregue sai da visão operacional (✅ 2026-07-30)

Pedido em `'entregue'` **nunca é excluído** — decisão explícita do Pablo: apagar levaria junto o `product_events` e os dados que alimentam os Relatórios, que já são reais e valiosos. Ele continua no banco e consultável; o que muda é só **onde aparece**. **Zero migration.**

**A causa raiz era duplicação, não um esquecimento pontual.** O conceito "pedido operacionalmente ativo" estava reescrito inline em cinco telas, em três grafias diferentes — por isso, quando o estágio `'entregue'` nasceu (item 1), três lugares foram atualizados e **dois ficaram para trás**. Agora o conceito mora em `src/data/orderStages.js`, que já era o dono do vocabulário de estágios:

- `FINAL_STAGE` (`'entregue'`), `isActiveOrder(order)` (não é rascunho e não foi entregue) e `isInWorkflow(order)` (ativo **e** já fora da Venda — o recorte das telas de trabalho).
- Consumido por `Dashboard`, `Orders`, `Design` (`isActiveOrder`), `Production` e `Conference` (`isInWorkflow`). O backend tem a cópia própria em SQL, sem import compartilhado — mesma situação já documentada de `ORDER_STAGES`.

**Os dois buracos que existiam:**
- **Fila de `/design`** filtrava só `!isDraft`. Como todo produto de um pedido entregue está com `designStatus = 'concluido'`, ele ficava parado na coluna "Concluído" **para sempre**. (Essa coluna crescer indefinidamente foi resolvido depois pela validade de 7 dias — ver seção própria.)
- **`GET /reports/bottlenecks`** usava `stage != 'venda'`, que **inclui** `'entregue'`. Agora é `stage NOT IN ('venda', 'entregue')` nas duas queries (`volumeByStep` e `stuckProducts`).
  - **Correção de registro, importante para não repetir o raciocínio errado**: a justificativa original que dei era "um pedido entregue com uma Costura que ninguém marcou como concluída". **Isso é bem mais difícil de acontecer do que parece** — o gate de sequência impede que as etapas de Conferência *comecem* antes de as de fabricação concluírem, e a trava de entrega exige as de Conferência concluídas. Ou seja, o caminho ingênuo é bloqueado (confirmado empiricamente: `409 "Não é possível iniciar Revisão/Finalização antes de concluir: Costura, Bordado, Corte"`). Os caminhos que **realmente** levam a um pedido entregue com etapa aberta são três: (1) uma **"outra operação" digitada à mão**, isenta do gate nos dois sentidos e portanto capaz de ficar `pending` para sempre sem travar nada — foi com ela que o cenário foi reproduzido; (2) mover uma etapa **para trás** depois da entrega; (3) adicionar uma operação nova a um pedido já entregue. O filtro continua certo — só é menos frequente do que a justificativa original sugeria.
- **`GET /reports/avg-time-per-step` NÃO foi filtrado, de propósito**: tempo médio é justamente estatística histórica; excluir o que já foi entregue destruiria a base de cálculo. **Gargalo é problema de hoje; média é memória.**

**Os entregues começaram como uma aba dentro de `/pedidos` e viraram tela própria (`/entregues`) em 2026-07-31** — ver seção adiante. O que a aba já resolvia continua valendo: a coluna "Prazo" vira **"Retirado em"** (`order.pickedUpAt`), que é o que se consulta num histórico — prazo de um pedido já entregue não diz nada.

**Limitação conhecida e aceita**: o `GET /orders` traz **todos** os pedidos e o filtro acontece no navegador. Hoje são ~30, irrelevante. Conforme os anos de Kavi acumularem entregas, cada carregamento vai baixar o histórico inteiro — **é isso que um dia vai forçar paginação ou filtro no servidor.** Não resolvido preventivamente.

**Verificado** por API (cenário montado até "entregue com etapa aberta", gargalos antes/depois, o carimbo de `picked_up_at`, e a confirmação de que pedido, etapas, histórico e tempo médio seguem intactos) e no navegador — incluindo o entregue sumindo de Produção/Conferência/Design **varrendo todas as abas de cada tela, não só a primeira**, e os detalhes do pedido entregue ainda abrindo com histórico.

### Relatório de prazo real venda → entrega (✅ 2026-07-30)

`GET /reports/lead-time` + uma seção nova no topo de `Relatórios`. Só existe porque a migration `0009` passou a carimbar `orders.picked_up_at` — é a primeira coisa a consumir esse dado.

- **Marco inicial: `orders.created_at`.** A escolha óbvia seria o evento `order_finalized` (o clique em "Finalizar Pedido"), semanticamente mais preciso — **mas o banco de produção tem ZERO desses eventos**: o evento só passou a ser gravado no item 3.3 e nenhum pedido foi finalizado pela tela desde então, então o relatório sairia vazio. **Distorção conhecida e escrita na própria tela**: `created_at` é quando a vendedora abriu "Novo Pedido" (a tela cria o rascunho na montagem); se ela abrir e só finalizar dias depois, a contagem começa cedo demais. Na prática é a mesma sessão, e o desvio é pequeno perto de um ciclo de semanas. **Um `COALESCE` do evento com o `created_at` foi descartado de propósito** — daria uma média com dois significados diferentes dentro dela, pior que um proxy consistente. Se um dia houver volume de `order_finalized`, aí sim vale reavaliar (e migrar a métrica inteira, não misturar).
- **Duas medidas, porque prazo real sozinho é número sem referência**: quanto levou (`picked_up_at::date - created_at::date`) e se cumpriu o prometido (`picked_up_at::date - deadline`; positivo = atraso, negativo = adiantado, `NULL` = pedido sem prazo). Quem não tem `deadline` entra na primeira e fica fora da segunda — daí o resumo mostrar "1 de 2" e avisar quantos ficaram sem prazo, senão o denominador confundiria.
- **Subtração de `::date`, não de `timestamp`**: a pergunta é "quantos dias" do jeito que uma pessoa conta, não frações de hora.
- **Duas queries** (agregado sobre todos os entregues + as últimas 20 linhas para a tabela), mesmo formato de `bottlenecks` — o resumo continua correto com centenas de entregas, sem mandar todas pela rede.
- **A API devolve `clientId` cru, não o nome montado no SQL** — `getClientDisplayName` é o único lugar que decide o que exibir de um cliente, e replicar aquele `COALESCE` na query criaria um segundo dono da mesma regra.
- **Sem filtro de período**, igual aos dois relatórios que já existiam. Quando o volume justificar, é aí que se pensa em recorte de datas.
- **Correção de localização feita junto**: `formatHours` usava `toFixed(1)`, que produz `"23.3 dias"` — ponto, não vírgula, num app inteiramente em português. Virou `toLocaleString('pt-BR')` via o helper `decimal()`. `formatDays` mostra inteiro sem casa decimal ("20 dias"), e só a média leva uma casa.
- **Verificação**: três cenários montados de propósito (**atrasado**, **adiantado** e **sem prazo**, com `created_at` retrodatado por SQL, já que a API não deixa escolher a data de criação), com **todo o resumo conferido contra a mesma agregação rodada em SQL cru** em vez de valores chumbados no teste. **Dois defeitos só apareceram ao OLHAR a captura, não nas asserções**: o "20.8" com ponto e uma frase torta na nota de rodapé.

O Cloudinary foi escolhido em 2026-07-06 pela facilidade de configuração *nessa escala*; **se a escala mudar, a razão da escolha muda junto**, então a análise a fazer é comparar Cloudflare R2 / Backblaze B2 / S3, que cobram por GB sem degrau. **Como o modelo de créditos funciona, porque não é óbvio**: 1 crédito = 1 GB armazenado **ou** 1 GB de banda **ou** 1.000 transformações. **Armazenamento acumula; banda zera todo mês** — então o orçamento mensal é "tudo que já foi guardado + o que trafegou no mês", e a folga para banda encolhe conforme o acervo cresce. Com ~2,3 MB por arquivo e um cenário de ~30 pedidos/mês, a projeção grosseira dá **uns 5 anos** até encostar nos 25 GB.

**⚠️ Achado de 2026-07-30: 75 arquivos no Cloudinary contra pouquíssimas linhas em `product_files` — ✅ limpo em 2026-07-31** (74 apagados, 1 preservado: o único referenciado no banco, que é o arquivo de teste antigo que o Pablo mandou deixar).

**A leitura original do achado estava errada e vale corrigir**, porque a conclusão prática muda: eu escrevi que o espaço estava sendo consumido por "lixo de teste" meu. Ao inventariar para apagar, a divisão real apareceu — **10 arquivos eram uploads de teste do TexFlow e somavam ~0 MB** (eram PNGs minúsculos); os **169,3 MB eram 64 imagens/vídeos de demonstração que o próprio Cloudinary instala em toda conta nova** (`sample`, `samples/coffee`, `samples/sea-turtle`, `cld-sample-*`...), sem nenhuma relação com o TexFlow ou com a Kavi. Ou seja: o consumo não era do uso real **nem** do meu lixo — era do acervo de demonstração que veio junto com a conta.

**Como conferir/limpar de novo** (o roteiro, já que não existe rota de delete no app): listar `cloudinary.api.resources()` para `image`/`raw`/`video` (paginando por `next_cursor`), extrair o `public_id` de cada `product_files.file_url` com `/upload/(?:v\d+/)?(.+?)(?:\.ext)?$`, e apagar a diferença com `cloudinary.api.delete_resources(lote, { resource_type })` em lotes de 100. **Reconferir contra o banco no momento de apagar**, não só no inventário — um arquivo enviado no meio do caminho não pode morrer por estar fora de uma lista velha. A API `cloudinary.api.usage()` **demora a refletir** a limpeza (o consumo é recalculado periodicamente), então não estranhe se logo depois ela ainda mostrar os números antigos.

## Gerente, etapa avulsa, excluir arquivo e feedback ao salvar (✅ 2026-08-03)

### PDF dando erro — não era bug do código (investigado 2026-08-03)

Vale registrar porque a investigação derrubou a correção "óbvia". Todo `.pdf` no Cloudinary voltava **HTTP 401 com `x-cld-error: deny or ACL failure`**, enquanto `.png` voltava 200 — o upload funcionava, o registro estava no banco, falhava a *entrega*. **Trocar `resource_type: 'auto'` para `'raw'` NÃO resolve** — testado subindo um PDF como `raw` na conta real: 401 igual. A correção é uma chave na conta (Console → Settings → Security → Restricted media types → desmarcar PDF), é **retroativa** aos arquivos que já existiam, e o Pablo aplicou. Não gaste tempo procurando conserto no `cloudinary.js` se isso reaparecer; confirme primeiro se a trava da conta voltou.

`DELETE /products/:productId/files/:fileId`, `SALES_ROLES` (que agora inclui o gerente) — exatamente quem sobe arquivo: a vendedora anexa referência, o design anexa o layout aprovado. **A produção consome o layout, não o administra.**

## Visão financeira para administradores (✅ 2026-08-04/05, três entregas)

Fecha o item registrado em 2026-07-31 como "o próximo grande item". **Escopo travado pelo Pablo antes de qualquer schema, e não deve crescer sem ele pedir**: é um **relatório sobre vendas e recebimentos**, não um sistema financeiro — sem contas a pagar, sem despesas, sem fluxo de caixa, sem DRE, sem nota fiscal. Mantém a fronteira declarada no topo deste arquivo; o dinheiro só aparece na medida em que já passa pelo TexFlow (`total_value`, `amount_paid`).

**Só `admin`.** `FINANCE_ROLES = ['admin']` é constante própria nas duas cópias da matriz, **e não `ADMIN_ONLY` reaproveitado**, mesmo sendo hoje o mesmo conjunto: são decisões independentes que apenas coincidem. Se um dia o gerente puder ver faturamento, mexe-se numa constante — com a compartilhada, o mesmo edit entregaria Configurações junto. O `gerente` fica de fora por decisão explícita do Pablo, mesmo acumulando vendedora + produção.

### O levantamento que mudou o plano (e por que ele foi feito antes de codar)

O Pablo propôs aproximar "quando o dinheiro entrou" pelo `updated_at` do pedido ou pela data do evento `payment_registered` mais recente, para não precisar de tabela de parcelas. **O levantamento contra o banco de produção mostrou que nenhuma das duas se sustenta**, e é por isso que a entrega 1 existe:

- **`updated_at` é mutável.** Ele se move em qualquer edição do pedido, então corrigir um prazo em setembro tiraria a venda de agosto do total de agosto — **o número de um mês fechado mudaria para trás**. (Verificado que `recalculateOrderTotal` **não** toca nele, então editar produto não desloca; o estrago era menor do que parecia, mas continuava desqualificante.)
- **O evento `payment_registered` tinha quatro furos**, todos visíveis em dados reais: o payload guardava o **acumulado**, não o que entrou; a sequência nem sempre cresce (um pedido real tem `640 → 320 → 640`); **o pagamento feito na própria venda não virava evento** (ver abaixo); e o log só existe desde 18/07.

Conclusão levada ao Pablo: aceitar a aproximação produziria **um número errado com cara de certo**, que é o pior resultado num relatório de dinheiro. Ele escolheu corrigir o evento (em vez de trocar a métrica ou criar `order_payments`).

### Entrega 1 — o evento de pagamento passa a guardar o que entrou

Dois problemas em `PATCH /orders/:id`, ambos corrigidos juntos:

1. **Pagamento e edição eram mutuamente exclusivos** (`isPayment = "amountPaid é o único campo"`). Como "Finalizar Pedido" manda `clientId` e `amountPaid` **juntos**, o pagamento da venda — normalmente o maior — era gravado como `order_updated`, cujo payload guarda só os *nomes* dos campos. **O valor não ia para lugar nenhum.** Em produção havia pedido com R$ 50 pagos e zero eventos de pagamento. Agora os dois eventos são **independentes**: finalizar com entrada gera os dois, que é a verdade.
2. **O payload virou `{ previous, current, delta }`.** O delta responde "quanto entrou" direto, e **delta negativo é correção de lançamento**, distinguível de recebimento — coisa que o acumulado sozinho não permitia.

Mais: **`SELECT ... FOR UPDATE`** antes do UPDATE (sem a trava, dois pagamentos simultâneos no mesmo pedido leriam o mesmo `previous` e gravariam deltas somando errado), e **valor repetido deixou de gerar evento** (antes gravava a cada clique em Salvar).

**`describeEvent` (`src/utils/events.js`) entende as DUAS formas, e isso não é transitório**: os eventos gravados até 04/08/2026 têm só `amountPaid`, e ler apenas a forma nova faria o histórico real exibir "R$ 0,00".

⚠️ **O deploy desta entrega inverteu a regra do projeto, de propósito.** A regra é backend primeiro, porque normalmente o front novo consome campo que só o backend novo devolve. Aqui era o contrário: com o backend novo e o front velho, o histórico mostraria "Pagamento registrado: R$ 0,00" (o front antigo lê `payload.amountPaid`, que deixou de existir); com o front novo e o backend velho, o ramo de compatibilidade renderiza certo. **Frontend primeiro era o lado inofensivo.** Vale reconhecer a inversão quando a mudança do front for puramente defensiva.

### Entrega 2 — a tela

`GET /finance/overview?month=YYYY-MM` (`backend/src/routes/finance.js`) e a página `/financeiro`, com item próprio no menu entre Relatórios e Configurações e `action="finance.view"` na rota.

**Tela própria em vez de seção dentro de Relatórios**, por três motivos: a preferência já registrada do Pablo (tela no menu, não aba dentro de outra tela); restrição por rota é mais limpa que por seção — o precedente de gatear por seção é Configurações, e existe só porque "Minha Senha" precisa ficar acessível a todos; e Relatórios é visível às vendedoras, então um bloco admin-only ali criaria uma página com conteúdo invisível para a maioria. Contrasta de propósito com `/entregues`, que **não** ganhou `action` por ser leitura para todos — aqui a restrição é o ponto.

**VENDIDO ≠ RECEBIDO, e a tela inteira preserva isso**: `sold` sai de `total_value` (o combinado) e `received` de `amount_paid` (o que entrou). **A palavra "receita" não aparece em lugar nenhum** — ela apagaria a diferença justamente onde importa; há checagem automatizada garantindo.

**As ressalvas ficam coladas no número que qualificam**, não num rodapé geral: a série ser por data do pedido, e a quebra por tipo considerar só produto com preço (produto sem preço fica **de fora**, não entra como zero). A vetorização não entra na quebra por tipo, por não pertencer a um tipo de peça.

**Números do momento vs. do mês**: "a receber" não pertence a mês nenhum — um pedido de julho ainda em aberto é dinheiro a receber hoje. Por isso os três cartões e a quebra por cliente são do momento, e só a série e a quebra por tipo respondem ao mês selecionado.

**A lista "Pedidos em aberto" existe porque "a receber" sem os nomes é um número que ninguém sabe cobrar.**

⚠️ **Fuso na virada de mês (a terceira vez que UTC morde neste projeto).** O banco roda em `Etc/UTC` e a Kavi opera em UTC−3: um pedido feito **31/07 às 21h30 no Brasil** está gravado como **01/08 00h30**. Todo agrupamento mensal converte com `AT TIME ZONE 'UTC' AT TIME ZONE 'America/Sao_Paulo'`. Verificado com um pedido montado exatamente nessa borda — sem a conversão seriam 3 horas de atribuição errada em toda virada de mês.

⚠️ **Ids de `bigint` viajam CRUS, como no resto da API.** O node-pg devolve `bigint` como **string**; `mapOrder` e a rota de clientes repassam sem converter. Uma primeira versão do `finance.js` fazia `Number(client_id)`, e a busca por igualdade estrita parou de casar: **toda linha da tabela por cliente saía "Cliente não informado"**. As 21 asserções passavam — o defeito só apareceu na captura de tela.

### Entrega 3 — a série de recebimento por mês

Sai de `product_events`, **não** de `orders.amount_paid`: a coluna só sabe o acumulado de hoje, e a pergunta é em **que mês** o dinheiro entrou.

- **`jsonb_exists(payload, 'delta')` é o filtro que separa as duas eras do evento.** Os eventos anteriores à entrega 1 guardam o acumulado; somá-los como entrada contaria o mesmo dinheiro várias vezes e inflaria o mês. Ficam de fora, e a tela informa desde quando a série vale. (`jsonb_exists()` em vez do operador `?` só para não deixar um ponto de interrogação solto no SQL, que confunde quem lê esperando um placeholder.)
- **`received: null` ≠ `0`, e a tela renderiza `—` para o primeiro.** Nos meses anteriores ao início da série o sistema realmente não guardava a data; exibir R$ 0,00 afirmaria que nada entrou, o que é falso e faria a série parecer uma queda brusca.
- **Soma líquida dos deltas**, com `corrections` numa coluna à parte que só aparece quando existe alguma — sem ela, um mês menor que o esperado ficaria inexplicável.
- **`sold` e `received` contam por datas diferentes** (data do pedido × data do pagamento), então um pedido de um mês pago no seguinte aparece em meses distintos nas duas colunas. A nota de rodapé diz isso, senão pareceria erro.
- **`receiptsSince` é derivado do próprio dado**, não uma data fixa no código: ninguém precisa lembrar de atualizar constante, e num banco novo a resposta continua certa.
- ⚠️ **`MIN()` sobre timestamp é formatado em SQL, não em JS.** O node-pg devolveria um `Date` interpretado no fuso do processo Node, e um `toISOString()` depois disso deslocaria o dia — e o mês, numa virada. Quarta aparição do mesmo tipo de armadilha.

### Limitações conhecidas e aceitas

- **"Recebido em julho" nunca vai existir.** O dado não foi gravado e não há de onde tirar. A tela é explícita sobre isso em vez de mostrar número inventado. Se um dia for necessário, o caminho seria a tabela `order_payments` com lançamento retroativo — a opção que o Pablo descartou por ora.
- **Excluir um pedido apaga os eventos de pagamento dele** (`ON DELETE CASCADE` em `product_events.order_id`), então um mês já fechado pode encolher. É coerente (dinheiro de pedido excluído não deveria contar), mas é **a via que resta para um número mensal mudar retroativamente**.
- **Metade dos pedidos "reais" em produção é lixo de verificação antigo** — `PED-2026-0025`, `0031` e `0032`, dos clientes "Cliente Verificacao ...", somando **R$ 864 de venda falsa**. O Pablo optou por deixar e decidir depois; até lá, o primeiro número que a tela mostra está contaminado.
- **Sem filtro de período além do mês**, igual aos outros relatórios. E a quebra por cliente é de todos os períodos, não do mês — o saldo em aberto só faz sentido acumulado.

### Lição de método reforçada aqui (duas vezes no mesmo dia)

**`innerText` devolve o texto JÁ transformado pelo CSS.** Rótulos com `text-transform: uppercase` não casam com a grafia do JSX. Isso apareceu na verificação da ficha impressa e de novo aqui — e na ficha foi pior que um falso negativo: tornou **falso-positivas** duas checagens de "a seção some", que passariam mesmo com a seção presente. Ao asserir sobre texto renderizado, normalize a caixa ou compare no DOM.

Também registrado: **não presuma a ordem de uma lista vinda da API**. `GET /orders/:id/events` devolve `ORDER BY created_at DESC` (mais novo primeiro, como a timeline precisa); um teste que usou `.at(-1)` esperando ordem crescente leu o evento errado e acusou três falhas inexistentes — foi o invariante "soma dos deltas = `amount_paid`" que denunciou o teste, não o código.

## Cancelamento de pedido e layout por pedido (✅ 2026-08-05)

Dois pontos levantados pelo Pablo como itens independentes, feitos um por vez.

### Cancelar pedido (migration `0013`)

**Cancelar NUNCA exclui nada** — o pedido, os produtos e todo o `product_events` continuam no banco e consultáveis. É o mesmo princípio já adotado para pedido entregue: o que muda é só *onde* ele aparece.

**A decisão estrutural: coluna `orders.cancelled_at`, NÃO um valor novo em `stage`.** O Pablo propôs um estado de saída paralelo a `'entregue'`; o levantamento mostrou que isso quebraria em silêncio:

- `PATCH /orders/:id/advance-stage` faz `ORDER_STAGES.indexOf(stage)`. Para um valor fora do array isso devolve **−1**, e a linha seguinte lê `ORDER_STAGES[-1 + 1]` = **`'venda'`**. Clicar em "Avançar etapa" num pedido cancelado o **ressuscitaria no começo do fluxo, sem erro nenhum**.
- E colocar `'cancelado'` *dentro* de `ORDER_STAGES` faria dele um **sétimo chip no tracker de todo pedido**, como se fosse etapa pela qual todos passam — além de `'entregue'` passar a "avançar" para cancelado.

Sendo ortogonal ao `stage`, o cancelamento **preserva até onde o pedido chegou**: a tela diz "cancelado na etapa Em produção", e reabrir devolve ao mesmo ponto. Cancelar na Venda e cancelar na Produção são situações muito diferentes (uma desperdiçou material), e substituir o `stage` apagaria isso. Mesmo desenho de `is_draft` (marcador paralelo à progressão) e de `picked_up_at` (carimbo de um evento).

- **`isActiveOrder` foi reaproveitado**, e é obrigatório que seja: é a abstração criada justamente porque esse conceito já ficou desalinhado em cinco telas quando `'entregue'` nasceu. Entrou `isCancelledOrder` na mesma família. **As três cópias em SQL foram atualizadas junto** (o `REAL_ORDERS` do Financeiro e as duas queries de Gargalos). O `lead-time` **não** precisou: como cancelar entregue é bloqueado e avançar cancelado também, os dois estados são mutuamente exclusivos por construção.
- **Duas rotas explícitas** (`/cancel` e `/uncancel`), não um toggle: um endpoint que inverte esconderia qual das duas coisas quem chamou queria, e um clique repetido faria o oposto do esperado. Ambas com `SELECT ... FOR UPDATE`.
- **Travas**: pedido cancelado não avança nem volta etapa (409 nas duas). Sem isso a trava seria só dica de tela e um clique reabriria o pedido pela porta dos fundos.
- **`SALES_ROLES`, que inclui o `design`** — o Pablo pediu "vendedora, gerente e admin", e eu apontei que `SALES_ROLES` traz o design junto (ele acumula a vendedora por decisão registrada). Ele confirmou usar a constante existente.
- **Pedido entregue não pode ser cancelado (409)** — decisão minha, não dele: a peça saiu e o dinheiro entrou, e registrar cancelamento ali seria erro que ninguém desfaz.
- **Financeiro: cancelado fica FORA DE TUDO** — vendido, a receber e recebido — por decisão explícita do Pablo, ciente da consequência: **dinheiro já pago num pedido cancelado some do relatório sem que nenhuma devolução tenha sido registrada**, porque o TexFlow não modela devolução.
- **Os cancelados aparecem numa seção do Dashboard, não em tela própria.** É um desvio consciente do precedente de `/entregues` e da preferência registrada do Pablo por tela própria: o raciocínio dele é que cancelamento é raro na Kavi e não paga um 11º item de menu. A seção **só existe quando há algum** — bloco vazio permanente seria ruído no retrato do dia.
- **Não foram bloqueadas as outras ações num pedido cancelado** (editar produto, registrar pagamento, "Voltar etapa"). O servidor barra só as de etapa; o resto segue o princípio de não adicionar gate que ninguém pediu.

### Layout aprovado por pedido (migration `0014`)

**Mudança de decisão do Pablo** em relação ao que estava registrado: o mockup aprovado é um só para o pedido inteiro, e subir num produto faz valer para todos. **`'referencia'` não mudou** — continua sendo do produto.

**Modelagem: `product_files` ganhou `order_id` e `product_id` virou nulável**, em vez de uma tabela `order_files` nova. É exatamente o caminho que `product_events` trilhou na migration `0004`. As alternativas descartadas: tabela separada duplicaria upload, exclusão e a integração com o Cloudinary e obrigaria o front a juntar duas fontes; copiar a linha para cada produto quebraria em produto adicionado depois e tornaria a exclusão ambígua.

- **As duas cascatas passam a fazer coisas diferentes, e é o desejado**: excluir um **produto** leva as referências dele mas **não** o layout (que tem `product_id` NULL); excluir o **pedido** leva tudo.
- **`CHECK` no banco** (`product_files_scope_check`) amarrando categoria e dono. Sem ele, um bug que gravasse layout com `product_id` **voltaria em silêncio ao comportamento antigo** — o arquivo apareceria só num produto e ninguém notaria.
- **O que fez isso ficar barato**: `fetchOrders` e `getProductById` dobram o layout do pedido dentro do `files` de cada produto, então `ProductFileList`, `ProductDetailPanel` e o selo "Layout aprovado" do card de Produção **não mudaram uma linha** — são genéricos por categoria.
- **A rota continua `/products/:productId/files`**, mesmo para o layout: o produto é por onde a pessoa chega (ela está olhando uma peça) e dele sai o pedido. Uma rota separada obrigaria a tela de Design a saber de qual pedido é o card antes de subir, sem ganho. No `DELETE`, o `:productId` vira escopo: aceita arquivo do produto **ou** do pedido dele, o que impede apagar arquivo de outro pedido informando um id qualquer.
- **A migration não desempata layouts duplicados de propósito**: se um pedido tivesse dois layouts em produtos diferentes, os dois viram layouts do pedido. Perder arquivo numa migration é pior que mostrar dois. (Nos bancos reais existe no máximo um por pedido, então o caso é teórico.)
- **Dica na tela**: o modal de arquivos diz "Vale para o pedido inteiro — aparece em todas as peças" sob "Layout aprovado". Sem isso alguém excluiria "o layout desta peça" achando que as outras seguiriam com o arquivo.
- **Premissa desatualizada corrigida**: o Pablo citou a ficha impressa como afetada. **Não é** — o campo "Layout aprovado" saiu da ficha em 2026-08-04, a pedido dele. As telas que dependiam eram Design (upload), Produção (selo) e a exclusão de arquivo.

**Erro meu na migration, registrado pela lição**: a primeira execução falhou porque eu zerava o `product_id` **antes** de remover o `NOT NULL`. **A transação reverteu tudo e o banco ficou intacto** — o migration runner funcionando exatamente como projetado (cada arquivo na sua transação). Ordem certa: `DROP NOT NULL` antes do `UPDATE ... SET product_id = NULL`.

## Possível expansão futura (não é prioridade agora)

Existe a possibilidade de, no futuro, o TexFlow ser adaptado para venda a outras confecções (modelo SaaS), não só uso interno da Kavi. O domain model atual (pedido → produtos → workflow independente, operações configuráveis) já é razoavelmente genérico e ajuda nessa direção, mas isso exigiria mudanças significativas de arquitetura: multi-tenancy (isolar dados por empresa), configuração por empresa das operações/catálogos, autenticação multiempresa, e decisões de modelo de negócio (cobrança, suporte, onboarding).

Isso deve ser considerado apenas mais para o final do projeto, ou quando o momento for adequado — não antes de o sistema estar sólido e validado no uso real da Kavi. Não adicione complexidade de multi-tenancy ou generalização prematuramente; construa pensando na Kavi primeiro.

## Development philosophy

These principles were explicitly agreed on with the user and should guide new work, not just the existing code:

1. Model the system after the confecção's real process — don't bend the process to fit software limitations (e.g. don't force a single fixed pipeline onto all products).
2. Think architecture and reuse before implementation.
3. Extract a reusable component whenever it makes sense — check `components/ui` before inlining new markup.
4. Avoid duplicating logic/markup (DRY).
5. Keep the structure scalable and consistent with conventional professional React apps (pages-as-folders, ui/layout split, per-feature CSS).
6. Keep responsibilities separated: components, pages, styles, data, and (future) services/hooks each in their own place.
